# Response to the review of the vehicle reversal split design

Design: [2026-11-04-vehicle-reversal-split-design.md](superpowers/specs/2026-11-04-vehicle-reversal-split-design.md) (now rev. 2)  
Review: [review_2026-11-04-21-04-32.md](review_2026-11-04-21-04-32.md)

All four findings are correct and are accepted. I reproduced the two behavioural ones (P1 and the first P2) before changing the design. Rev. 1 claimed that link's heading margins prevented re-links. That claim was wrong and is withdrawn.

## Changes

| Comment | Resolution | Where |
|---|---|---|
| **[P1]** The heading margins do not stop link from undoing a reversal split | I took the first option the review offers: a mechanism specific to reversal splits. `_Stages` keeps `reversal_cuts` (raw ID → cut frames), and link gets a new keyword, `forbidden_cuts`. A pair `(di, dj)` is never a candidate when `di`'s lineage has a span of raw `r` ending before a cut `c` of `r` and `dj`'s lineage has a span of `r` starting at or after `c`. The check reads the full lineage, so it still holds after screen drops rows next to the cut, switch cuts either side again, or dedup merges into either side. It applies in scored mode (in `score_candidates`, next to the `_resplit` check, before gating) and in legacy mode (the pair is infeasible in `_legacy_matches`'s cost matrix). `link.keep_splits` was not used: it would change link for every switch split, and it allows a join when another track lies between the halves, which is wrong across a reversal. A chain `A → X → B` through a third track is not blocked. It needs `X` to fit in the one-frame gap left after rows are dropped at the cut, and success criterion 4 now says explicitly that it is not covered. A component check is the planned follow-up (§8). The rev. 1 `validate()` warnings are removed. Tests added: your counterexample (which must re-link without `forbidden_cuts`, so the test proves the fix is needed), shortened sides, a re-split side, legacy mode, and identical candidates when `forbidden_cuts` is empty. | §2, §3.4, §3.5, §6.2, §8, success criterion 4 |
| **[P2]** The earliest smallest cosine does not find the turn | I chose localization over parity. Within a run the cut is now at the largest velocity change `\|v_a − v_b\|`, with the earliest row winning ties. This is the tie-breaker switch already uses for saturated heading rows (`turn` in `_heading_reversal`). It is declared as the first deliberate difference from the script, so the script's cut on this fixture is a bias that is fixed, not a behaviour to keep. Parity in §6.3 now means cutting the same runs, and the cut inside a run is checked against the velocity-change rule. Your straight-line fixture is in §6.1 with an exact assertion of row 30, together with a noisy version. | §3.2 step 5, §3.3, §6.1, §6.3, success criteria 1–2 |
| **[P2]** A byte-identical disabled ledger conflicts with the new config block | Byte equality is kept for the track file only. The baseline is defined as the output of the pre-change code on a fixed synthetic vehicle fixture, recorded under `tests/refine/data/reversal_baseline/` by the plan's first task. Ledger events must be equal field by field, and the header may differ only by `config.reversal` and `dnt_version`. No legacy serialization mode is added: a header that records every setting is worth more than byte-identical old ledgers. | §6.2, success criterion 5 |
| **[P2]** Renumbering raw input IDs cannot keep the key | The test now builds the work table with `io.to_work`, keeps `raw_id`, and renumbers only `work.track` before proposing; the keys must be equal. A separate test checks that changing the raw ID in the lineage changes the key. | §6.2 |
