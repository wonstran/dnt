Both points are accepted. Both compatibility paths are now **preserved**, not excluded. Findings marked *verified* were checked against 0.3.2.4 (`git show 063a9b5:src/dnt/track/tracker.py`, `Tracker._build_boxmot_tracker` and the `MOTBaseConfig` methods).

1. **High: restricting `extra_kwargs` broke a working 0.3.2.x tuning path.** **Accepted.** Every factory-level key that worked is preserved with identical results, and a regression test pins down the path you identified.

   *Verified:* 0.3.2.4 built `{"tracker_type": model.value}` and merged `config.to_kwargs()` into it, with `extra_kwargs` taking precedence over the fields. It then overwrote `device` and `half` with the `Tracker` arguments, which default to `"auto"` and `False` and so are never `None` by default. Finally, it kept only non-`None` `create_tracker` parameters. So `extra_kwargs={"evolve_param_dict": {"track_thresh": 0.7}}` did tune ByteTrack, and `tracker_config`, `per_class`, `tracker_type` and (for ReID trackers) `reid_weights` were effective too. Three more paths were not effective: `device` and `half` (whenever the `Tracker` argument was not `None`), `reid_weights` on trackers without ReID, and every non-factory key.

   New [§2.8](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#28-factory-level-keys-in-extra_kwargs-032x-compatibility) has a table covering each key:
   - **`evolve_param_dict`** becomes the base arguments **verbatim**, keeping BoxMOT 16's full-replacement meaning: keys it leaves out fall back to *constructor* defaults, not YAML defaults. With no dnt fields set, `create_tracker` receives the identical dict, so behaviour is identical. Tuning fields set as well are validated and overlaid.
   - **`tracker_config`**: its YAML defaults become the base. That is equivalent to BoxMOT loading the file itself, because it's the same `{k: v["default"]}` expression. Fields are overlaid.
   - **Both keys together** raise `ValueError`. In 0.3.2.x, `evolve_param_dict` silently won.
   - **`per_class`** and **ReID `reid_weights`** keep their 0.3.2.x precedence, where the `extra_kwargs` value wins.
   - **`tracker_type`**: a value equal to `model` is a no-op; any other value raises `ValueError`.
   - **`device` / `half`** keep the exact 0.3.2.x precedence, where the `Tracker` argument wins unless it is `None`. A conflicting value that used to be silently ignored now raises.
   - **Silently ignored keys** now raise, and any other tracker parameter is validated like a field. This follows the patch-release policy that silent misbehaviour becomes an error.
   - **Deprecation:** the preserved passthroughs emit `DeprecationWarning`, because BoxMOT 25 has no `evolve_param_dict` and they are removed in 0.4.
   - **Unvalidated contents:** keys inside a user's `evolve_param_dict` or `tracker_config` are passed through unvalidated, as in 0.3.2.x, and dnt warns about any key BoxMOT would ignore. §2.8 states that the effectiveness guarantee does **not** cover these BoxMOT-format passthrough contents.
   - §2.3 has been rewritten so that the base arguments come from BoxMOT's YAML, `tracker_config`, or `evolve_param_dict`, and §2.2's `extra_kwargs` sentence now points to §2.8.
   - **Saved configs:** a legacy file's `extra_kwargs` follows the same table, so a saved `evolve_param_dict` keeps working.

   Tests (§2.6, new factory-key group):
   - **The regression you described:** `ByteTrackConfig(extra_kwargs={"evolve_param_dict": {"track_thresh": 0.7}})` makes `create_tracker` receive exactly `{"track_thresh": 0.7}`. The built tracker has `track_thresh == 0.7` and `match_thresh` equal to the constructor default of 0.8 (not the YAML's 0.9), matching 0.3.2.4.
   - The same config saved by 0.3.2.4 as `passthrough/bytetrack_evolve.yaml` loads to the same result.
   - Every other table row has its own test.
   - **Golden** (§5.3): the passthrough config is added to the golden set and must match 0.3.2.4 byte for byte.

2. **High: old `to_dict()` → `from_dict()` round-trips changed untuned results.** **Accepted.** Old dicts now migrate through the existing `from_dict()`, with no API change for callers.

   *Verified:* 0.3.2.4's `to_dict()` is `_yaml_safe(asdict(self))`, which is the same full mapping the YAML export writes.

   Changes ([§2.7](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#27-saved-configs-format-version-and-032x-migration)):
   - **The version marker is now a real field.** `MOTBaseConfig` gains `dnt_config_version: int = 2`, keyword-only. Every mapping 0.3.3 produces (`to_dict()`, exports, `asdict()`) carries it, and `XConfig(**cfg.to_dict())` keeps working. No 0.3.2.x mapping has it.
   - **Why it had to be a field.** Response 2 kept the marker in files only. That would have made 0.3.3 dicts ambiguous for OC-SORT, Deep OC-SORT, HybridSORT and BoostTrack, whose field sets are identical in both versions, so a 0.3.3 round-trip could have been mistaken for a legacy one.
   - **One detection rule for dicts and files.** `from_dict(data, legacy="auto")`, where `"auto"` is the **default**, uses the same exact-shape rule as the file loaders: no version key, plus exactly the 0.3.2.4 field set. A persisted 0.3.2.x `to_dict()` dict loaded with the **unchanged** `from_dict(d)` call therefore migrates: untouched defaults become BoxMOT defaults, and results are byte-identical. `from_legacy_dict()` stays as an explicit alias.
   - **Review 2's concern still holds.** Partial or hand-written dicts lack the full key set, so they are strict. `SFSORTConfig.from_dict({"det_thresh": 0.9})` still raises.
   - **One stated exclusion: `XConfig(**old_dict)`.** Unpacking an old dict into the constructor is plain construction, and a constructor cannot see where its values came from. dnt emits a `UserWarning` when every tuning field equals its 0.3.2.4 default and at least one of those differs from BoxMOT's value, which is the pattern an unpacked old dict produces. The warning points to `from_dict`. The changelog names the exclusion.

   Tests (§2.6, saved-config group). New fixtures are generated **with 0.3.2.4** in the baseline environment: `dict/<tracker>.json`, produced by `XConfig().to_dict()`, alongside the existing eight YAML files.
   - **Old dict round-trip:** for all 8 trackers, `XConfig.from_dict(d)` with no new arguments gives the untuned arguments.
   - **0.3.3 round-trip:** for all 8 trackers, `from_dict(cfg.to_dict()) == cfg`, both untuned and tuned, with no migration warning. This explicitly covers the four trackers whose field sets are unchanged.
   - Tests also cover the constructor-splat warning, `legacy=True` / `False`, and an unknown version.
   - **S3(a′)** now covers both files and dicts, plus the passthrough paths.
