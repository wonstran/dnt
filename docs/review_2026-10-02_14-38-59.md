# Review of P3 VLM verification plan

Reviewed: 2026-10-02 14:38 EDT  
Plan: [2026-10-02-track-refinement-p3-vlm.md](superpowers/plans/2026-10-02-track-refinement-p3-vlm.md)

## Comments

1. **[P1] Keep the async client on one live event loop across stage calls.** `_run` creates and closes a new loop for every `ask_many` (plan lines 1382–1389, 1510–1514), while the backends retain one `AsyncOpenAI` or `AsyncAnthropic` client (lines 1016–1018, 1075). The same runner is used for switch, screen, and multiple link passes. A client's pooled connections can therefore belong to an already closed loop when the next stage asks a question. A local HTTPX keep-alive reproduction returned HTTP 200 on the first `asyncio.run` and `RuntimeError: Event loop is closed` on the second. Keep a loop alive for the runner's lifetime and close the client on that loop, or give each loop its own client. Test successive stage calls against a local HTTP endpoint, including the notebook path; the current fake backends have no loop-bound connections and conceal this failure.

2. **[P1] Allocate the call budget to complete questions in priority order.** The semaphore limits concurrent questions, but `_reserve` allocates individual calls as those questions interleave (plan lines 1414–1418, 1456–1508). With two questions, `votes=3`, `max_calls=3`, and `max_concurrency=2`, the extracted runner spent two calls on the first question and one on the second; both returned `error="budget"`. There was enough budget to decide the highest-priority question, but no question completed. Later questions can likewise consume the calls an earlier question needs after a transient failure. Add admission or reservation rules that preserve question priority while accounting for cached votes and retries. Test multiple votes and delayed retries with concurrency greater than one and a tight budget; the existing priority tests force concurrency to one.

3. **[P1] Validate cached answers as strictly as fresh model replies.** `AnswerCache.get` checks only that `answer` is a string and converts `confidence` with `float` (plan lines 517–525). The runner uses that result without validating its option or confidence (lines 1474–1494). A readable cache entry containing `answer="different"` and `confidence=NaN` produces a successful verdict; the confidence check in `interpret` is false for NaN, so a pending SPLIT becomes `VLM_ACCEPT`. I reproduced the cached verdict with zero backend calls. Reject non-finite or out-of-range confidences, boolean confidence values, and answers outside the question's options before treating an entry as a hit. Add malformed-but-readable cache cases and a routing test proving that such an entry cannot accept an edit.

4. **[P1] Preserve overlapping observations in screen evidence.** DROP/RECLASS planning uses `_clean`, which excludes every row marked occluded, and only adds a context frame if at least one clean row remains (plan lines 1821–1862). An always-overlapping track consequently has no screen evidence at all, even with context frames enabled. This affects exactly the duplicate, in-vehicle, and rider hypotheses that rely on overlap; an uncertain event or unresolved rider subtype can never reach the VLM. The extracted planner returned an empty packet for an all-occluded screen event. Design §7.1 requests observed crops for screen events and clean crops for identity comparisons. Sample screen evidence from observed rows, retaining useful overlapping crops and context, and test an uncertain overlapping screen event through `refine`.

5. **[P1] Show unsupported segments when verifying a partial screen edit.** The partial-event branch selects crops only inside `params.spans` and creates one row A (plan lines 1852–1862). It discards the unsupported segments entirely. Design §6.2 explicitly requires supported and unsupported segments in separate rows; the motivating case is a pending ID switch between a pedestrian and a passenger. The model and reviewer need that distinction to assess the proposed partial edit. Build labeled rows for both sets of segments, explain their meaning in the screen prompt, and test the composite image and prompt for a partial DROP/RECLASS. Displaying segment scores in the HTML does not supply the missing visual evidence.

6. **[P2] Match the actual `id_map` type in clip snippets.** `_snippet` looks up `str(t)` keys (plan line 3250), but `renumber` returns `dict[int, int]`, and the refiner passes that map directly to `write_review` (lines 3388–3401). Every real review snippet therefore contains `track_ids=[]` and produces no clips. The unit tests pass artificial string-keyed maps, so they miss the mismatch. Use integer keys or convert the map at the call site, and assert nonempty, correctly renumbered IDs in an HTML page produced by `refine`.

7. **[P1] Delete only images owned by the generated report.** `_remove_own_files` unlinks every `*.jpg` in `OUT.review/` (plan lines 3316–3322). A rerun with no pending events therefore deletes an unrelated `my-photo.jpg` placed in that directory; I reproduced this with the extracted helper. The preservation test checks only `keep.txt`, which avoids the broad deletion pattern. Track the generated image names in a manifest or otherwise establish ownership before deleting them, and add a `keep.jpg` preservation case. Include the image directory in input/output collision handling if a generated image could overwrite a recorded input.

8. **[P1] Bind saved review choices to the proposals they reviewed.** The localStorage key uses only `document.title`, and saved choices are restored solely by the sequential event ID (plan lines 3173–3189). Reusing the same output name for changed inputs or settings can give a different proposal the same ID, such as `switch-r0-000001`; its accept/reject choice and class are then restored from the previous run and exported for the new proposal without another selection. Namespace saved choices by the report's defining inputs and validate each stored choice against `event.proposal_key`. Test regenerating the same report path/title with the same event ID but a different proposal, and ensure the old choice is not restored.

## Verification scope

Reviewed the plan against the current P1/P2 interfaces and the design spec. Ran isolated reproductions using the plan's runner, cache, evidence planner, and review helpers, plus a local HTTPX keep-alive test. These confirmed the budget, cached-confidence, screen-evidence, partial-evidence, snippet-ID, and cleanup findings. The complete proposed implementation and its test suite were not run.
