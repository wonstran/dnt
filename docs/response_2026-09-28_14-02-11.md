1. **P1: preserve unique observed rows when merging overlapping tracklets.** **Accepted.**

   - **Fix (Task 9, `apply.merge_chains`).** A chain now keeps the set of frames it already has. A later member loses only its rows on those frames, and its other rows are kept, even inside the overlap span. This matches §6.3: "The overlapping rows from j are dropped on merge." The docstring states the rule.
   - **Tests:**
     - `test_merge_keeps_unique_rows_inside_a_sparse_overlap` (Task 9): A has frames 0–8 and 11, and B has frames 9–12. After merging, the frames are exactly 0–12, frames 9 and 10 come from B, and the frame-11 row is A's.
     - `test_sparse_overlap_link_keeps_unique_observed_rows` (Task 15): the same geometry end to end. Stage 3 accepts the pair through the overlap gate (`g = -2`, IoU 1 on frame 11), and after `merge_chains` frames 9 and 10 are still observed.
   - The existing `test_merge_chains_keeps_earliest_id_and_drops_overlap_rows` passes unchanged, because a contiguous overlap behaves the same under both rules.

2. **P1: do not suppress a whole-track screen event when every segment supports it.** **Accepted.**

   - **Fix (Task 12, `propose_screen`).** When every segment reaches `reject_below` for a hypothesis, the event covers the whole track (`spans: None`) and is **scored by its weakest segment**. Its signals and params come from that segment, plus `all_segments: True` and the per-segment scores.
   - **Why not the whole-track score.** Mixing segments can hide what each one shows, as the reviewer's example of two static spots far apart illustrates. The whole-track score is now used only when a track has no segments. A comment in the code records why.
   - **Test** (`test_every_segment_static_gives_a_whole_track_event`): two 12-second stationary segments about 670 px apart, with a pending cut between them.
     - Before the fix: the whole-track static score was 0, so no event was written.
     - Now: a whole-track `DROP{static}` with `spans: None`, scored at the segment value 0.611.

3. **P1: reject non-numeric values in the remaining input columns.** **Accepted.**

   - **Fix (Task 6, `io`).** `_read_numeric_csv` takes a `check_cols` argument, so each format validates every column it uses:
     - dnt track files: all ten columns (score, class, filled-row flag and `r4` included);
     - MOT files: the first seven (up to the confidence column);
     - context files: the first eight (up to the class column).

     A bad value raises the §10 `ValueError` naming the file and line. It is no longer silently turned into `-1`, or into an observed row when the bad value is in the flag column.
   - **Tests:**
     - `test_read_tracks_rejects_nonnumeric_score_cls_flag_and_r4`: a bad score, class, `r3` flag, or blank `r4` on line 3 raises an error naming "line 3". The file's line 2 is a valid filled row, so the check does not reject the flag value 1 itself.
     - `test_valid_filled_flag_is_still_removed`
     - `test_read_context_rejects_nonnumeric_class`

4. **P2: align P1's claims with what it can apply.** **Accepted.** The chosen fix is to state the limitation, not to add an apply path. A minimal decision/apply path would partly duplicate Plan 4's replay, and that replay has to reconcile proposal keys, rounds, and re-proposal, which P1's events are already built for.

   - **Plan goal (line 5)** now says P1 *proposes* every kind of edit and *applies only confident edits*: screen drops and reclasses, normal and static-wait links, orphan drops, and fills. It also says that every motion-only switch split (capped at 0.70, below the 0.90 accept threshold) and every occlusion-witnessed link (capped at 0.75, below 0.80) is recorded as `HUMAN_PENDING` and not applied until Plan 3 or Plan 4.
   - **API docs (`docs/api/refine/index.md`, Task 17)** gain a "Current limitations" note saying the same in user terms.
   - **Changelog (Task 17)** now says the release "proposes" these edits. It adds a separate bullet naming what is applied and what is only recorded as pending.
   - **Already pinned by a test:** `test_default_config_no_video_all_three_stages_score` asserts that switch and screen proposals in the uncertain band are `HUMAN_PENDING`, and that the confident link is applied.
