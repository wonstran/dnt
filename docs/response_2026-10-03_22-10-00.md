All five comments are correct. I checked the code claims first: `EvidenceBuilder` reads `lineage[0]` as track A and `lineage[1]` as track B, and link events store `[di.lineage, dj.lineage]` in track order (`link.py`, `evidence.py`); `write_review` selects only `HUMAN_PENDING` events; `lineage_of_rows` returns one min-to-max span per raw ID; `track_embeddings` and `dense_track_embeddings` read the raw ID's embeddings across whole spans. The spec is revised. Nothing is implemented, and none of the new rules has been run.

## Changes by comment

| # | Comment | Resolution | Where |
|---|---|---|---|
| 1 | **[P1]** Dense A/C below the proposal gates is not a cannot-link pair | Separated proposal eligibility from component safety. Cannot-link rule 2 no longer uses `min_overlap_seconds` or `min_observed`: any two tracks in components being joined, with at least one overlapping frame, are blocked when `shared >= conflict_min_shared` and `co_occupancy >= cooccur_hi`, whether or not a `MERGE` event exists for them. `conflict_min_shared` (default 3) is a new config field, so one coincident flicker frame cannot veto a join, which would otherwise happen at tiny overlaps. Tests: bridge cases with A/C at 29 frames (below the span gate) and 7 rows (below `min_observed`), and a 2-frame co-observation that does not block. | §3.5, §6, test 7 |
| 2 | **[P2]** Canonical lineage order breaks the `tracks` correspondence | Took the first option. Event `lineage` stays in `tracks` order, as link events and `EvidenceBuilder` expect. Only the key is computed from a canonical copy, through a new optional `key_lineage` keyword on `Event.propose`. `n_a` and `n_b` are documented as matching `tracks[0]` and `tracks[1]`. Test 13 now also asserts track/lineage/`n_a`/`n_b` correspondence and crop labels, using the reviewer's 125/122 example. | §3.3, test 13 |
| 3 | **[P2]** Skipped merges are not selected into the report | Defined the selection: the report shows pending events with controls (as before) and, in a separate "Skipped merges" section, **read-only** cards for `MERGE` events skipped as `conflict`. They have no controls and add nothing to the exported decisions, because a cannot-link pair cannot be overridden in this version. `redundant` edges stay ledger-only. The page is written when either group has a card and removed only when both are empty. Test 15 is the reviewer's run: only accepted edges, one skipped as conflict, no pending events. | §3.4, §5, test 15 |
| 4 | **[P2]** 125/134 ratio is conditional; test 1 expectation is wrong | Both are corrected. `6 / min(30, n_134)` is now stated as a lower bound of 0.20 (reached when `n_134 >= 30`), the penalty as "at least a third", and the pair as not a candidate at all if `n_134 <= 15`. Its outcome is open until the plan's first task measures the counts. Test 1 now expects 176 output rows (183 in, 7 shared frames each lose one), `dropped_rows` 7 and seven named dropped rows. | §3.2, test 1 |
| 5 | **[P2]** Downstream lineage still includes dropped observations | Chose exclusion. `_Stages` keeps an `excluded` map (`raw_id` to frames dedup dropped), and `lineage_of_rows(rows, excluded=None)` splits a raw ID's span at each excluded frame strictly inside it (`[122, 10, 30]` with frame 20 excluded becomes `[122, 10, 19]` and `[122, 21, 30]`). The span format is unchanged, so `track_embeddings`, `dense_track_embeddings` and `EvidenceBuilder` need no change. Every `lineage_of_rows` call after dedup receives `excluded` (link, orphan and fill); `MERGE` events keep their as-proposed lineage. New test 18 uses an interior deletion with a recording fake appearance provider and checks both the embedding requests and the evidence frames. | §3.5, §10, test 18, criterion 3 |

## Not verified

- Nothing was run. The new rules (the safety check, `key_lineage`, the span splitting, the report selection) are specified and tested on paper only.
- I did not enumerate every `lineage_of_rows` call site. I listed `link.py` (descriptors and pair events), `refiner.py` (fill and the orphan pass) from a search of the files; the plan should confirm the full list, including any call in `screen.py`, before relying on "every call after dedup".
- The numeric defaults, including the new `conflict_min_shared = 3`, are starting values and have not been fitted to data. The 125/134 outcome is explicitly open.
- I did not check how the review page's JavaScript and `decisions.json` export handle a section of read-only cards, or whether existing review tests assume every card has controls.
