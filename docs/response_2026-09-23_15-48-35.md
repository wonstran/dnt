# Response 2: dnt 0.3.3 correctness and packaging design

Responding to: [review_2026-09-23_15-48-35.md](review_2026-09-23_15-48-35.md)  
Previous round: [review 1](review_2026-09-23_15-39-32.md) / [response 1](response_2026-09-23_15-39-32.md)  
Spec (revision 3): [2026-09-23-dnt-0.3.3-correctness-packaging-design.md](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md)

All five points are accepted and the spec is revised. Findings marked *verified* were checked against the 0.3.2.4 source (`git show 063a9b5:src/dnt/track/tracker.py`) or the BoxMOT 16.0.11 wheel from PyPI. Point 4 also uncovered a new issue, **SF-SORT silently clamping values**, which is now handled as well.

---

1. **High: an untuned config exported by 0.3.2.x would change results.** **Accepted.** The spec now defines an explicit migration rule, and the saved-config guarantee is stated narrowly.

   *Verified:* 0.3.2.4's `export_yaml` / `export_config_to_yaml` write `asdict(config)` as a flat mapping. That mapping contains **every** field (`model`, `per_class`, `extra_kwargs`, `reid_weights`, and all tuning fields) with dnt's old defaults, and has no version marker. The old defaults do differ from BoxMOT's. For example, ByteTrack uses 0.5 / 0.8 against BoxMOT's 0.6 / 0.9, and BoT-SORT's `new_track_thresh` is 0.6 against 0.7. Your example stands.

   New [§2.7](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#27-saved-configs-format-version-and-032x-migration):
   - **Migration rule.** In a 0.3.2.x file, each tuning field is compared with the **0.3.2.4 dnt default** for that class. The defaults are stored as `LEGACY_0324_DEFAULTS` and checked against `063a9b5`.
     - A value **equal** to the old default is migrated to `None`, which means BoxMOT's default. The user never set it, and 0.3.2.x never applied it.
     - A value that **differs** is kept as user-set, so it now takes effect. That is the agreed B1 behaviour.
     - `model`, `per_class` and `reid_weights` load unchanged, since 0.3.2.x did pass those to BoxMOT.
   - **Result:** an untouched 0.3.2.x export migrates to exactly the untuned arguments, so tracks are byte-identical. The new success criterion **S3(a′)** covers this, and a test uses the eight real files exported by 0.3.2.4 in `tests/data/legacy_0.3.2/`.
   - **Stated limitation.** In a legacy file, a value the user deliberately set *equal to* the old default can't be told apart from an untouched one, so it migrates too. The load warning lists every migrated field so the user can set it again explicitly. The changelog states this limitation.

2. **High: the saved-config exception also discarded newly supplied settings.** **Accepted.** Legacy input is now recognised by an explicit rule and is never guessed from a plain dict. Both paths are tested.

   Changes (§2.7, §2.2):
   - **Format version.** 0.3.3 exports write `dnt_config_version: 2`. Such files are **strict**. The key is file metadata and is never treated as a setting. An unknown version raises `ValueError`.
   - **Legacy detection.** A file is treated as a 0.3.2.x export only if it has **no version key** *and* its key set is **exactly** the 0.3.2.4 field set of the class named by its `model`. Only 0.3.2.x's export functions produce that exact shape, so a hand-written partial file is strict. `legacy="auto" | True | False` on `import_yaml` and `import_config_from_yaml` lets the caller override the detection. `legacy=True` on a file that isn't legacy-shaped raises an error.
   - **`from_dict` is always strict.** Your example, `SFSORTConfig.from_dict({"det_thresh": 0.9})`, now raises `ValueError` with the hint "use `high_th`". Old dicts can be migrated only by asking for it: `MOTBaseConfig.from_legacy_dict(data)`, which applies the same shape check.
   - **Nothing is silently discarded, even in legacy files.** A non-effective field whose legacy value *differs* from the old default raises `ValueError`, because the user asked for a setting that can't take effect. Only untouched defaults are dropped, and those are listed in the warning.
   - **Tests** (§2.6, saved-config group):
     - the 0.3.2.4-exported default files migrate to the untuned arguments
     - an edited effective value is applied
     - an edited non-effective value raises
     - a new-format file and a plain dict with the same content take the strict path
     - `legacy=True` misuse raises

3. **Medium: `offsets[0]` contradicted the reference-time anchor.** **Accepted.** Decision: `ref_time` is always the time at `ref_frame`, and `offsets[0]` must be 0.

   [§3.1](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#31-synchronizer-timeline-b12) now uses *T*₀(*f*) = *R* + (*f* − *r*)·*p*₀, so *T*₀(*r*) = *R* exactly. Video 0 has no previous video to be offset from, and `ref_frame` / `ref_time` already place it completely. A non-zero `offsets[0]` raises `ValueError("offsets[0] must be 0; position video 0 with ref_frame/ref_time")`.

   This is consistent with the patch-release policy that silent behaviour becomes an explicit error: 0.3.2.4 ignored every offset. The `[2, 0]` example has been replaced by a test that expects this error. The spec now includes the public docstring text, which states the anchor rule and the relative, per-video meaning of `offsets[i]` for *i* ≥ 1.

4. **Medium: the tests couldn't detect a wrong audit.** **Accepted.** The spec now requires source-backed evidence for every setting and behaviour tests that fail when a setting is a no-op. Propagation tests are no longer described as proving effect.

   Changes:
   - **Source evidence.** New [Appendix A](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#appendix-a-source-evidence-for-effective-parameters) lists, for every exposed effective field of all eight trackers, the `file:line` and code in the 16.0.11 source where the value is read after construction. Examples are `ocsort.py:341` `if iou_left.max() > self.asso_threshold:` and `sfsort.py:253` `mth = self.match_th_first`. It also records where the non-effective fields have no read site. *Verified* by searching the wheel's code tokens (docstrings and comments excluded) and then reading the individual sites.
   - **The evidence stays tied to real code.** `tests/data/boxmot_16.0.11_param_evidence.json` mirrors the appendix. A test asserts that each recorded code string appears at its `file:line` in the **installed** BoxMOT source, and that `EFFECTIVE_PARAMS` equals the set of fields with evidence. Checking that a name appears in a constructor signature no longer counts as evidence.
   - **Behaviour tests** (§2.6 group 3). Each one runs the tracker on the synthetic scenario twice, once at the default and once at a probe value, and asserts an observable difference. A no-op field would therefore fail. The required families are:
     - detection threshold: set above the stub confidence → no tracks
     - low-score band
     - track lifetime: below the 8-frame gap → new ID after the gap
     - confirmation: `min_hits` / `n_init` = 20 → the first 19 frames disappear
     - match threshold: an extreme value → more IDs
   - **The weaker claim is stated openly.** Fields whose effect the synthetic scenario can't show are listed explicitly as **evidence-only**, and the spec and docs claim only source evidence for them. Those fields are `appearance_thresh`, `proximity_thresh`, `with_reid`, `cmc_method`, `frame_rate`, `asso_func`, `delta_t`, `inertia`, `max_iou_dist`, `max_cos_dist`, `nn_budget`, `ema_alpha` and `mc_lambda`. A required probe can move to that list only with a written reason, which the maintainer reviews in the plan.
   - **Renamed test groups.** The earlier "two non-default values" tests are now called **propagation tests** and are explicitly *not* evidence of effect.
   - **New finding: silent clamping (*verified*).** SF-SORT passes its settings through `_resolve_or_default`, which **clamps** them to a range (`sfsort.py:104-111`, `:336-340`). For example, `match_th_first=0.8` silently becomes 0.67, and `low_th` is capped at `high_th`. That is another way a user setting silently fails to take effect. dnt now checks those ranges and raises `ValueError` (§2.2). The plan's re-check applies the same treatment to any other tracker that turns out to clamp.
   - **`extra_kwargs`** is validated against the same allowlist, so it can no longer pass BoxMOT arguments that haven't been verified.
   - **S2** has been reworded to match.

5. **Medium: any baseline failure could weaken the eight-tracker guarantee.** **Accepted.** Golden generation now fails closed.

   Changes ([§5.3](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#53-tests)):
   - **Pre-flight checks** run before any tracker, and a failure aborts the run with nothing written. They cover the environment lock, the clip (opens, frame count, fps, SHA-256), the baseline detection file's layout, the ReID weights' SHA-256, and a writable output directory.
   - **Any tracker exception aborts** the run (non-zero exit, no partial manifest) unless it matches an entry in `tests/golden/known_baseline_defects.yaml`. An entry has to match on exact exception type, a fully matching message regex, and the innermost dnt or BoxMOT raise site. It also records the written root cause with a code reference, the reviewer and date, and a stored traceback.
   - **The defects file starts empty.** Entries are added only in a separate commit that the maintainer reviews, after the failure has been diagnosed as a genuine 0.3.2.4 defect and not an environment, data or weights problem. `make_golden.py` never writes to it.
   - **Stale entries abort too.** If a listed defect no longer reproduces the same way, generation aborts, so outdated exemptions can't linger.
   - S3(b), the changelog item and the §7 risk row now describe this fail-closed rule.
