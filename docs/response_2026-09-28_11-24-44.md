1. **Medium: a corrupted feature cache — error or cache miss when the verified video exists?** **Accepted.** The chosen behavior: **a cache miss whenever the verified video is available, and an error only when it isn't.**

   **Why.** The rev. 6 wording treated the feature cache like the other recorded inputs. They are different:
   - `tracks`, `video`, `context`, and `hints` are **defining inputs**: they determine the proposals, so a mismatch means "different input", and `apply` must refuse.
   - The feature cache is **derived** entirely from the defining inputs and the encoder settings. A mismatched cache can always be rebuilt from verified sources, so refusing would help no one.

   **Changes** (§4.2, "Inputs for replay"):
   - **Hash rule narrowed.** The `ValueError` rule for hash mismatches now names only the defining inputs. The feature cache is stated as a derived input with its own rule.
   - **Three cache states.** The cache is *valid*, *missing* (not found at its override or recorded path), or *invalid* (it exists, but the SHA-256 or key differs, or it can't be read). A table gives the behavior for each state, with and without the verified video:
     - valid → use the cache;
     - missing, with video → cache miss, logged at INFO, recompute;
     - invalid, with video → cache miss, logged at **WARNING** with the recorded and found hashes, recompute; the invalid file is left untouched;
     - missing, without video → `ValueError`, "feature cache not found at …";
     - invalid, without video → `ValueError`, "feature cache at … does not match the ledger (recorded …, found …)".

     The two error messages differ, so a missing cache is distinguishable from a corrupted one.
   - **Only checked when needed.** The cache is read and checked only when stage 1 or 3 will re-run with appearance. Otherwise it is not touched.
   - **After a recomputation:**
     - `apply` writes `OUT.features.npz`, never over the rejected file.
     - The new ledger header records the new cache, with `features_recomputed: true`.
     - On CPU the recomputed embeddings reproduce the original output. On a GPU, floating-point nondeterminism can move a score that sits right on a threshold. That is why the flag is recorded.
   - **§5.3 aligned.** Its "discarded and recomputed" sentence now applies explicitly to `refine`, and points to §4.2 for `apply`.
   - **§10** has separate rows for "missing or invalid cache, video available" (cache miss) and "neither available" (error).

   **Tests** (`test_replay.py`, "Missing video and cache"):
   - **New case: modified cache with the verified video present (CPU).** No error: a WARNING with both hashes, then recomputation. The output equals the run that used the original cache. The modified file is unchanged on disk, and the new `OUT.features.npz` matches the header's new `sha256`.
   - **Error messages distinguished.** Video removed and cache modified → "does not match", with both hashes. Video removed and cache removed → "not found".
   - **Recomputation flag.** Cache removed, video present (CPU) → the equality check now also asserts `features_recomputed: true`.
   - **New case: cache not needed.** A modified cache when neither stage 1 nor stage 3 re-runs (only an orphan-pass decision is overridden) → the cache is not read, and there is no warning or error.
