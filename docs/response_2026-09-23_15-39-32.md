# Response: dnt 0.3.3 correctness and packaging design

Responding to: [review_2026-09-23_15-39-32.md](review_2026-09-23_15-39-32.md)  
Spec (revision 2): [2026-09-23-dnt-0.3.3-correctness-packaging-design.md](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md)

All five comments are accepted, and the spec has been revised. Each response below says what changed and what the change rests on. Findings marked *verified* were checked against the source: `src/dnt/shared/synhcro.py` and the BoxMOT 16.0.11 wheel from PyPI.

---

1. **Synchronizer's time advance when `ref_frame` is nonzero.** **Accepted.** The spec now gives the formula.

   You're right. `ref_time` is the time *at* `ref_frame`, so the next video starts `(n₀ − ref_frame)` frames after `ref_time`, not `n₀` frames after it. *Verified* in `synhcro.py`: `add_unix_time` computes `ref_time + (f − ref_frame)·1000/fps`, and `process()` resets `ref_frame` to 0 but never advances `ref_time`. `offsets` is length-checked and then ignored.

   New [§3.1](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#31-synchronizer-timeline-b12):
   - Video 0: *T*₀(*f*) = *R* + (*f* − *r* + *o*₀)·*p*₀
   - Video *i* ≥ 1: *T*ᵢ(*f*) = *E*ᵢ₋₁ + (*f* + *o*ᵢ)·*p*ᵢ, where *E*ᵢ₋₁ = *T*ᵢ₋₁(*n*ᵢ₋₁)
   - *p*ᵢ = 1000/fpsᵢ, and *o*ᵢ is an integer offset in video *i*'s own frames. Positive means a gap, negative means an overlap, and each offset is relative to the previous video's end.
   - Values stay unrounded until output, so rounding error doesn't accumulate across videos.

   Your example is now the unit test: 100 frames at 25 fps with `ref_frame=25` gives *E*₀ = *R* + 3000 ms. The test also covers a 30 fps second video with offsets `[0, 5]`, `[2, 0]` and `[0, −3]`. A single video with zero offsets stays byte-identical to 0.3.2.4. Two related changes: the B12 row in §3 now points to §3.1, and the "confirm semantics before coding" deferral has been removed.

   **Decision for you:** the spec defines offsets as relative to the previous video's end, not cumulative from video 0. That is my reading of "offsets in FRAMES" per video. If you meant cumulative offsets, only the definition of *E*ᵢ₋₁ changes; tell me and I'll update §3.1.

2. **The byte-identical guarantee needs a fixed dependency environment.** **Accepted.** The guarantee is now scoped to a recorded environment, and BoxMOT is pinned exactly.

   Changes:
   - **Exact pin:** `boxmot==16.0.11` replaces `<17` ([§4.1](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#41-pyprojecttoml)). *Verified* on PyPI: the release sequence is 16.0.10 → 16.0.11 → 17.0.0, so 16.0.11 is the last 16.x and the exact pin costs users nothing.
   - **Stored snapshot instead of installed YAML:** S3(a) now compares the untuned arguments against a **committed** 16.0.11 YAML snapshot (`tests/data/boxmot_16.0.11_yaml_defaults.json`). A separate test fails if the installed BoxMOT's YAML differs from that snapshot. This addresses your point that comparing against the installed YAML "proves only consistency with that installation".
   - **Recorded reference environment** (new [§5.1](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#51-reference-environment-the-scope-of-the-byte-identical-guarantee)):
     - `tests/golden/reference-env.txt` is a fully hashed `uv pip compile` lock at the versions dnt last ran with: torch 2.10.0, ultralytics 8.4.14, boxmot 16.0.11, numpy 2.4.2, pandas 2.3.3, opencv 4.13.0.92, and others.
     - The 0.3.2.4 worktree is installed as the lock plus `pip install --no-deps -e <worktree>`, so its missing BoxMOT upper bound can't pull in the incompatible newer API.
     - The comparison venv uses the same lock.
     - Both runs write their package versions, Python version, torch build and GPU into a manifest. `make_golden.py` and the golden tests refuse to run on any version mismatch.
   - **Narrower wording:** S3 and the changelog now make the byte-level claim only "with the dependency versions in `tests/golden/reference-env.txt`". The version-independent claim is S3(a): identical arguments reach the pinned BoxMOT 16.0.11.
   - **Non-determinism:**
     - Golden tracking runs on the CPU.
     - Detection is run twice in the baseline environment to measure determinism. A documented tolerance applies only if those two runs differ.
     - Tracking consumes the stored baseline detections, so detection variance can't leak into the tracking comparison.

3. **SF-SORT's handling permits the original silent-settings bug.** **Accepted.** Non-effective fields now raise an error, and saved configs follow an explicit compatibility rule.

   I checked this against the 16.0.11 source instead of deferring it (*verified*). SF-SORT reads **none** of the five `BaseTracker` fields that dnt exposes.
   - `SFSORT.__init__` derives `det_thresh` from `high_th` itself and passes it to `BaseTracker`. A user-supplied `det_thresh` would therefore raise a duplicate-keyword `TypeError` inside BoxMOT.
   - `max_age` only changes `BaseTracker.max_obs`, which SF-SORT never reads.
   - `asso_func` only builds an association function that SF-SORT never calls.
   - `min_hits` and `iou_threshold` are not read at all.

   Because the same risk applies to every tracker, I audited all eight. One more non-effective field turned up: **BoostTrack's `asso_func`**, which appears only in BoxMOT's docstring. HybridSORT's `asso_func` *is* effective, through `asso_func_name`.

   The changes are in the new subsection "Effective parameters and non-effective fields" in [§2.2](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#22-config-classes), and in §2.3.
   - **Allowlist per tracker.** `EFFECTIVE_PARAMS[tracker]` holds the tracker's own constructor parameters plus only the `BaseTracker` fields that tracker reads. The audit table is in the spec. Validation uses this allowlist; accepting a field in `__init__` or `**kwargs` no longer counts.
   - **Setting a non-effective field** to anything other than `None` raises `ValueError` with a hint. For example: "`det_thresh` has no effect on SF-SORT in BoxMOT 16; use `high_th`." Similarly, `max_age` points to `marginal_timeout` / `central_timeout`, and the other fields say "no SF-SORT equivalent; remove the argument".
   - **Loading a saved config** (`from_dict`, `import_yaml`, `Tracker(config_yaml=…)`) drops non-effective keys with one `DeprecationWarning`. YAML exported by 0.3.2.x always contains them with old default values, and those values never had any effect. So dropping them exactly preserves 0.3.2.x behaviour and doesn't break users' saved files.
   - **Removal:** the fields are removed in 0.4.
   - **Tests** (§2.6): every non-effective field raises. Loading 0.3.2.x-style configs warns and then builds. `EFFECTIVE_PARAMS` is snapshot-tested against the audit table, and every entry must be a real constructor or `BaseTracker` parameter.
   - **Re-checking:** the implementation plan starts by re-confirming every audit row line by line against the pinned source.

4. **The listed tests do not exercise S1.** **Accepted.** A wheel-installed pipeline smoke test has been added, along with a concrete stub detector.

   Changes:
   - **Stub detector** (new [§5.2](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#52-fixtures-and-support-code)): `tests/support/synthetic.py` provides `make_synthetic_video()` and `StubDetector`. `StubDetector.detect()` has the same call signature and output as `Detector.detect()`. It builds `DET_FIELDS` rows from ground truth with seeded noise and dropouts, and it writes the same headerless file. It uses no model and no network. It is a plain module, so it can run outside the repository.
   - **Wheel smoke test** ([§5.3](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#53-tests), `slow`):
     1. Build the wheel.
     2. Create a clean **Python 3.11** venv and install the wheel into it.
     3. Copy the support module and `smoke_pipeline.py` into a temp directory outside the repository, and run them with the venv's Python.
     4. The script first asserts that `dnt.__file__` is in the venv's `site-packages`, not in `src/`.
     5. It then runs the stub detector → `Tracker(ByteTrackConfig())` → `interpolate_tracks_rts(track_file=…)` (covering B3) → `link_tracklets` → `Labeler().draw_tracks(label_class=True)` (which needs the packaged `.names` files, covering B7).
     6. It asserts the outputs are non-empty, the gap was filled, and the labelled video has 150 frames.
   - **S1 wording:** S1 now names this test and says "detect with the stub detector (no model)".
   - **CI:** the wheel job runs on Python 3.11 so that S1's "clean Python 3.11 venv" is what is actually tested ([§5.4](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#54-benchmark-ci-and-environment)).

5. **The golden tests cover only two of eight trackers.** **Accepted.** Golden coverage now includes all eight trackers.

   The golden run now records untuned tracks for ByteTrack, BoT-SORT, OC-SORT, Deep OC-SORT, StrongSORT, HybridSORT, BoostTrack and SF-SORT.
   - Each run uses the tracker's no-argument dnt config on the stored baseline detections, on the CPU.
   - ReID trackers use the committed `osnet_x1_0_msmt17.pt` weights.
   - S3(b) now claims byte-level equivalence for all eight, with one explicit exception. If a tracker cannot run at all on 0.3.2.4, `make_golden.py` records it in the manifest as failed, with the error. For that tracker the test checks only that 0.3.3 completes and produces the track schema, and both the test output and the changelog name the exemption.
   - To keep eight CPU runs (five of them with ReID) practical, the spec recommends a reference clip of at most about 60 s, and records the clip's duration and hash in the manifest.
