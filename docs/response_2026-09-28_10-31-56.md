# Response: follow-up review of the track refinement design

Responding to: [review_2026-09-28_10-31-56.md](review_2026-09-28_10-31-56.md)  
Previous round: [review](review_2026-09-28_09-53-41.md) / [response](response_2026-09-28_09-53-41.md)  
Design (revised, rev. 5): [2026-09-27-track-refinement-design.md](superpowers/specs/2026-09-27-track-refinement-design.md)

All six comments are accepted. Comments 2–4 are about the same mechanism (re-proposal during replay). They are fixed together by three changes:
- the ledger records every input, and `apply` verifies them;
- a stage re-runs when it owns a changed decision, not only when its input changed;
- matching uses an immutable proposal key, stored separately from the final edit.

---

1. **High: the promised default no-video run cannot start.** **Accepted.** There is no default frame rate, because every threshold in seconds depends on it and a guess would silently change them all. Instead the frame rate becomes an explicit run input.

   - **Resolution order** (§5.1): `refine(..., fps=...)` / `--fps`, then `RefineConfig.fps`, then the video.
     - An explicit value that differs from the video's rate by more than 1% logs a warning, and the explicit value wins.
     - With no video and neither setting, `refine` raises `ValueError` before any processing, asking for `fps=`.
     - The ledger header records the value and its source, and `apply` reuses it.
   - **Success criterion 1** now reads: the default config, with no video and `fps=` given, on an installation with no `post-*` extras. All three proposal stages score the tracks.
   - **Tests** (`test_minimal_install.py`, extended):
     - A fixture with an injected fragment, an injected takeover, and a static box, run with `fps=10` and no video. The ledger must hold proposals from stages 1, 2, and 3, so the test proves scoring actually ran, not just that the run started.
     - The same run without `fps` raises `ValueError` before processing.

2. **High: `apply` lacks the inputs required for re-proposal.** **Accepted.**

   - **The ledger header records every input** (§4.2). `inputs` holds `tracks`, `video`, `context`, and `hints`, each with its path (as given and resolved) and its SHA-256 (the fingerprint, for the video). The header also records `fps` with its source, and `frame_size`.
   - **`apply` takes its inputs from the header** (§2.4, §4.2). The new API is `TrackRefiner.apply(ledger, decisions=None, *, tracks=None, video=None, context=None, hints=None, vlm=True, fill=True, out)`. The CLI is `dnt-refine apply --ledger L [--tracks T] [--video V] [--context C] [--reclass-hints R] …`. The positional `TRACKS` is gone.
     - **Overrides change only locations.** Every input's hash is verified against the header before processing. A mismatch raises `ValueError` naming the input and both hashes. `apply` never re-proposes with different inputs; the fix is to run `dnt-refine run` again.
     - **Missing files.** A missing recorded `tracks`, `context`, or `hints` file is an error. A missing video only logs a warning: embeddings come from the cache, and new events that need evidence images become `HUMAN_PENDING` without images.
     - **No new inputs.** An input the original run did not have (e.g. `context` when the header says `null`) is rejected.
   - **Tests** (`test_replay.py`):
     - A run with context and hints leaves a `SPLIT` pending, and `apply` then accepts it. The output tracks equal those of a fresh `refine` whose fake VLM accepted the split directly, with the same set of applied proposal keys. This equivalence is also stated in §4.2.
     - An overridden context path with different content, a missing hints file, an added context file, and a missing video are each tested.

3. **High: rejecting a link does not trigger re-proposal.** **Accepted.** The replay trigger is widened (§4.2).

   - **New rule.** Each override is resolved to its event's `proposal_key`. An override that differs from the recorded decision marks that event as **changed**. The first stage that has a changed input **or owns a changed event** re-runs, and so does every later stage.
   - **Why re-running is safe.** Proposals are deterministic, so on an unchanged input they come out with the same keys. The overridden decisions are applied by key, and the stage continues. In stage 3, re-assignment then runs without the newly rejected edge, even though the stage's input table is unchanged.
   - **Success criterion 3** is updated to match.
   - **Tests** (`test_replay.py`):
     - A pending `LINK` from a `refine` run is rejected through `apply --decisions`. Stage 3 re-runs and proposes the alternative as a new event.
     - The earlier in-run test of rejection inside `refine` (`test_link.py`) is kept.

4. **High: the content key conflicts with VLM redirection.** **Accepted.**

   - **Proposal and edit are separate** (§4.1).
     - `kind` and `params` now always hold the **proposal**, and never change.
     - A new field, `edit: {kind, params} | None`, holds what is actually applied. It differs from the proposal when the VLM redirects the event (§7.2), or a person picks another class.
     - `apply.py` applies `edit` only.
     - `signals.proposed` is removed, because it is no longer needed.
   - **`key` is renamed `proposal_key`** (§4.2). It is the SHA-256 of the stage, the *proposed* kind, the lineage, and the proposal's defining params. It is computed before verification and never changes. A re-proposed event with the same key takes over the recorded decision, VLM answer, and `edit`.
   - **Tests:**
     - `test_verify.py`: a `DROP` answered as a rider gets a `RECLASS` edit, while `kind`, `params`, and `proposal_key` are unchanged.
     - `test_replay.py`: a redirected screen event survives a stage 2 re-run caused by an unrelated split decision. It keeps its `RECLASS` edit with no VLM call.

5. **High: inheriting a raw-track hint into every segment can reclass a pedestrian.** **Accepted.** Raw-track hints are treated as **unlocalized** after a split (§2.5, §6.2). They are not re-run or localized per segment: `ReClass` judges a whole raw track from a sample of its frames, so no hint can say which part of a split track it describes.

   - **When a hint is localized.** Only when the scored unit covers its whole raw track: no applied `SPLIT` on that raw track, and whole-track rather than segment scoring. Only a localized hint contributes `ramp_P` or settles the subtype.
   - **Unlocalized hints.** `ramp_P` counts as 0, and the subtype is chosen by the VLM. The hint is recorded in `signals.hint_unlocalized` and shown on the review card. It is kept out of the VLM prompt so that it doesn't bias the answer.
   - **Test** (`test_screen.py`): a mixed pedestrian/rider track with a strong raw hint (`cls 3`, 0.95), split at the change.
     - The pedestrian segment gets no `RECLASS`.
     - The rider segment is reclassed from motion cues, with the subtype chosen by the VLM.
     - An unsplit fast track with the same hint still takes its subtype from the hint.

6. **Medium: the video cache key misses late-frame changes.** **Accepted.**

   - **New fingerprint** (§5.3): the SHA-256 of the **entire file** (8 MiB chunks), plus the file size and frame count. It is computed once per run and shared by the cache key, the ledger header, and `apply`'s input check. Its cost is about 1 s per 1–2 GB, which is small next to decoding.
   - **Rejected alternatives.** Partial hashes, and hashes of size plus modification time, are explicitly not used.
   - **Test** (`test_fingerprint.py`): two 65 MiB files that differ only in one byte after the 64 MiB mark get different fingerprints despite the same size, and a cache built with one is not reused with the other.
