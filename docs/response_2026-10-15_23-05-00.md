# Response to the review of the vehicle re-classification plan

Plan: [2026-10-15-vehicle-reclass.md](superpowers/plans/2026-10-15-vehicle-reclass.md) (now rev. 2)  
Review: [review_2026-10-15-22-36-11.md](review_2026-10-15-22-36-11.md)  
Design: [2026-10-15-vehicle-reclass-design.md](superpowers/specs/2026-10-15-vehicle-reclass-design.md) (rev. 2, unchanged)

Both findings are correct and accepted.

- **Finding 1.** `_ask_vlm` rebuilt each track ID from the question tag with `int(...)`, so a float `track` column (`1.0`) raised `ValueError` after the model had answered. That aborted the run instead of falling back.
- **Finding 2.** The only multi-frame vote test had one class winning on both vote count and confidence sum, and no test sat at the default `min_support` boundary. So both demonstrated mutations survived.

The design already says the right thing: §5.2 weights votes by confidence and breaks ties by votes, then by class ID, and §9 asks for support "at and just below `min_support`". Only the plan changes.

## Changes

| Comment | Resolution | Where |
|---|---|---|
| **[P2] 1.** Track IDs are rebuilt from question tags | `_ask_vlm` keeps a list `asked` of the **original** track IDs, filled alongside `questions`, and zips it with the verdicts. Results are keyed by the same objects the caller passed in, and nothing is parsed back out of the tag. The tag is diagnostic text only. It is built with a new display helper `_tag_id(t)`, which shows an integral float or numpy scalar as an integer (`1.0` → `vehclass:1`), so tags and cache keys are the same for int and float IDs. The warning logs the ID with `%s`. New tests: `test_ask_vlm_keeps_original_ids` (a `1.0` key and an `int` key both come back unchanged), `test_tag_id`, and the integration test `test_vlm_with_int_or_float_track_ids`. That last test runs once with `int` and once with `float` track IDs. In both runs the track goes to the VLM, the answer writes bus, the decision layer is `vlm`, the tag is `vehclass:1`, and the output `track` column is unchanged in values and dtype. Review Focus item 1 now names float track IDs. | Task 6 Step 3 and Step 5 (code and interface), Task 7 Step 1, Review Focus |
| **[P2] 2.** The vote tests do not pin the algorithm | **Helper tests (Task 5):** `test_vote_confidence_sum_beats_vote_count` uses the reviewer's case: 4 bus votes at 0.3 (sum 1.2) and 3 truck votes at 0.9 (sum 2.7) over 10 frames, so truck wins with support 0.3. `test_vote_equal_score_more_votes_wins` gives bus 2 × 0.45 and truck 1 × 0.9; both sums are exactly 0.9 in binary floating point, and bus wins on votes. `test_vote_equal_score_and_votes_lower_class_wins` checks bus over truck and car over bus. **Integration tests (Task 7):** `test_support_exactly_at_min_support_decides` uses the same 10 decoded samples (frames 0, 5, …, 45), with three empty frames. At the default `min_support=0.3`, truck decides through `redetect` with `n == 10` and support exactly 0.3. `test_support_just_below_min_support_goes_on` sets `min_support=0.31`, and the track falls back to car. | Task 5 Step 1, Task 7 Step 1 |

## What I ran

- **Task 5 code and tests.** I extracted Task 5's code and tests from the revised plan into a scratch directory: **21 passed**. Then I applied the reviewer's count-only mutation (winner key `(-count[c], c)`). Exactly one test failed: `test_vote_confidence_sum_beats_vote_count`.
- **The `>` mutation of the support check** lives in `VehReClass.re_classify` (Task 7). By construction it fails `test_support_exactly_at_min_support_decides`, because support 0.3 is not `> 0.3`, so the track falls back to car instead of being decided as truck. I did not run that mutation; it needs the Task 7 class, which does not exist yet.
