# Follow-up review of the track refinement design and response

Reviewed: 2026-09-28 10:31 EDT  
Design: [2026-09-27-track-refinement-design.md](superpowers/specs/2026-09-27-track-refinement-design.md) (rev. 4)  
Response: [response_2026-09-28_09-53-41.md](response_2026-09-28_09-53-41.md)

The response addresses the earlier interpolation and protected-gap issues in the written design. The following issues remain in rev. 4.

## Comments

1. **[High] The promised default no-video run still cannot start.** Success criterion 1 says a run with no video and the default config completes (design line 66; response lines 104–117). But `fps` defaults to `null` (design line 750), while §5.1 requires either a video or `RefineConfig.fps` and otherwise raises an error (lines 307–310). Set a documented default FPS, require `--fps` and change the success criterion, or supply FPS through another defined input. Add an actual default-config/no-video test that reaches stage scoring.

2. **[High] `apply` lacks the inputs required for downstream re-proposal.** The response says a changed decision re-runs downstream stages (response lines 36–50), but the `apply` CLI accepts only tracks, ledger, optional decisions, and video (design line 155). Re-proposed screening needs the original context and ReClass hints (design lines 169–176, 447–475), and linking can need context boxes as occlusion witnesses (lines 524–528). The ledger header records neither file nor its hash (line 264). Specify how `apply` finds and validates these exact original inputs, expose them in the API/CLI if needed, and test replay after changing a split with context and hints present.

3. **[High] Rejecting a link does not meet the stated trigger for re-proposal.** The replay rule starts re-proposal at the first stage *whose input tracks differ* because of an upstream decision (design lines 271–280). Rejecting a pending `LINK` changes no input to the link stage; the input table is identical, so the rule re-applies its recorded events and never runs the promised reassignment (response lines 75–87; design lines 561–564 and 938). A decision change must invalidate and re-propose its own stage, even when the stage input is unchanged. Test this case directly with `apply --decisions`, not only rejection inside the initial `refine` run.

4. **[High] The content-key definition conflicts with VLM redirection.** The key hashes the event's kind and defining params (design line 269), while VLM verification may change a proposed `DROP` into a `RECLASS` and change its reason or class (lines 636–642). On replay, the same proposal is a `DROP`, so a key recomputed from it cannot match the earlier redirected `RECLASS`; the prior answer and decision are lost, contrary to the response's key-reuse claim (response lines 38–45). Define and retain an immutable *proposal* key before verification, separate from the final edit kind/params, and test key matching after a redirected screen event.

5. **[High] Inheriting one raw-track hint into every split segment can auto-reclass a real pedestrian.** The response explicitly applies a ReClass hint to every descendant of the raw ID (response line 30; design line 175). `ReClass` produces one result per raw track from selected frames; a high rider hint gives `ramp_P = 1` on *each* segment, so `S_rider = 1` and the hint supplies the subtype without a VLM call (design lines 468–478). For a pedestrian segment followed by a rider segment, both become riders after a correct split, defeating the new segment-aware safeguard. Treat raw-track hints as unlocalized evidence after a split, or rerun/localize hints per segment; test a mixed pedestrian/rider track with a strong raw-track hint.

6. **[Medium] The video cache key does not detect every changed video.** The response says any changed video invalidates cached embeddings (response lines 89–102), but the design hashes only the first 64 MiB plus file size and frame count (design lines 328–337). Two videos with the same prefix, size, and frame count but changed frames later will share the key and reuse stale crops. Use a full-content hash or a documented verified fingerprint that covers all frames used for embeddings; include a test modifying a frame beyond the first 64 MiB.

This is a static review of the response and revised design; implementation tests were not run.
