# Review: vehicle re-classification implementation plan

Reviewed: 2026-10-15 22:36:11 EDT  
Plan: [2026-10-15-vehicle-reclass.md](superpowers/plans/2026-10-15-vehicle-reclass.md)  
Design: [2026-10-15-vehicle-reclass-design.md](superpowers/specs/2026-10-15-vehicle-reclass-design.md), revision 2

The plan incorporates the previous design review's corrections. Two issues remain: a VLM-path failure for integral float track IDs, and missing tests for central voting requirements. Both are P2 findings to address before executing the plan.

## 1. [P2] Preserve track IDs instead of reconstructing them from question tags

**Location:** Task 6, lines 1233–1249; Task 7, lines 1524–1532 and 1727–1735.

`_ask_vlm` formats the original ID into `Question.tag`, then recovers it with `int(q.tag.partition(":")[2])`. A DataFrame whose `track` column contains integral floats is accepted by `_read_tracks` and works through size calculation and re-detection. If an undecided track reaches the VLM, ID `1.0` produces `vehclass:1.0`, and parsing the result raises:

```text
ValueError: invalid literal for int() with base 10: '1.0'
```

This occurs after the question has been asked, aborts classification rather than falling back, and prevents output from being written. The DataFrame contract specifies required columns without requiring an integer storage dtype. The existing float-frame test does not exercise float track IDs or VLM result association.

**Requested change:** Retain the original track ID alongside each question and zip those IDs with returned verdicts. Keep the tag as diagnostic text rather than using it to reconstruct application data, and use `%s` for logging the retained ID. If integral numeric IDs need canonical tags, normalize their display separately. Add a regression with `track.astype(float)` that reaches layer 3, receives a valid answer, writes the expected class, and preserves the input's track column. Pair it with the integer-ID version to check equivalent results.

**Verification:** Executed the plan's extracted `VehReClass` and `_ask_vlm` code with its fake detector/reader and a stubbed successful `VLMRunner.ask_many`. A track ID of `1.0` reproduced the exception at the tag-parsing line. No backend request was made.

## 2. [P2] Add voting tests that distinguish the specified algorithm from simpler, incorrect versions

**Location:** Task 5, lines 800–829; Task 7, lines 1336–1357 and 1722–1725. Design §9 explicitly requires support at and just below `min_support`.

The tests check support values of 0.1, 0.4, and 1.0, but do not test acceptance exactly at the default 0.3 boundary. The multi-frame example also gives the same class both the most votes and the largest confidence sum, so it does not establish that confidence weights determine the track winner.

I confirmed these gaps with two independent mutations of the extracted plan code:

- Changing `v.support >= self.min_support` to `v.support > self.min_support` still gives **52 passed, 5 deselected**.
- Replacing the winner key `(-weight[c], -count[c], c)` with the count-only key `(-count[c], c)` also gives **52 passed, 5 deselected**.

The second mutation changes classification: four bus votes at confidence 0.3 total 1.2, while three truck votes at confidence 0.9 total 2.7. The specified winner is truck; the count-only implementation chooses bus.

**Requested change:** Add an integration test with ten decoded samples, those four bus votes, three truck votes, and three unmatched frames. At `min_support=0.3`, truck must decide via `redetect` with support 0.3. Raising `min_support` just above 0.3 must force the next layer/fallback. This case catches both demonstrated mutations. Add helper tests for the specified equal-score tie breakers: more votes first, then lower class ID.
