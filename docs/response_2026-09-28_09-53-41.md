1. **High: screen can drop the valid part of an ID-switched track.** **Accepted.**

   - **Switch now runs before screen** (§3). A track that follows two objects is cut before either part is judged. The reason for screening first ("a pole must not be linked to a pedestrian") still holds, because linking remains after screening.
   - **Screening is segment-aware for unresolved switches** (§6.2). A track can still hold two objects when:
     - a `SPLIT` is `HUMAN_PENDING`, or
     - a stage 1 candidate scored below `switch.reject_below` but at least `screen.segment_at` (default 0.3).

     Their cut frames divide the track into segments, and each hypothesis is scored per segment.
     - If only some segments support the hypothesis, the event is a **partial** `DROP` or `RECLASS`, with `params.spans`.
     - It is capped at `screen.mixed_score_cap` (0.75, below `accept_above`), so it is never auto-applied.
     - If accepted, only rows inside `spans` change.
   - **Hints after reordering.** ReClass hints still work: a hint applies to every segment descended from its raw ID, using the new per-event `lineage` (§2.5, §4.1).
   - **Tests** (§11.1, `test_screen.py`): a pedestrian segment followed by an in-vehicle segment.
     - With the split applied, only the second track is dropped.
     - With the split pending, the result is a partial `DROP` that is never auto-applied, and accepting it keeps the pedestrian rows.
     - With a sub-threshold candidate (S = 0.35), there is still no whole-track auto-drop.

2. **High: a human-accepted split cannot receive downstream links on replay.** **Accepted.** Replay now **re-proposes** downstream stages (§4.2), instead of keeping conditional proposals for both outcomes. Re-proposal is simpler, and it also covers rejected links (comment 5).

   - **Lineage and content keys.** Each event records the raw rows its tracks are made of (`lineage`) and a content `key`: a hash of the stage, the kind, the lineage, and the defining params. A decision therefore survives renumbering.
   - **What `replay`/`apply` does:**
     - A stage whose input is unchanged re-applies its recorded events.
     - From the first stage whose input changed, that stage and every later one re-propose.
     - Re-proposed events that match an earlier `key` take over its decision and VLM answer. Only new events are routed: to the VLM, or with `--no-vlm` to `HUMAN_PENDING` in a new review round.
   - **Determinism** (success criterion 3, revised):
     - A decisions file that changes nothing gives byte-identical output, with no re-proposals and no VLM calls.
     - The same inputs, ledger, decisions, and VLM cache always give the same output.
   - **Embeddings.** The embedding cache and the occlusion mask no longer depend on decisions (§5.3), so re-proposal never re-encodes frames.
   - **Knock-on fix.** Before, the reference case's occlusion-witnessed link could only appear if the truck split was auto-applied. It now also appears after a reviewer accepts a pending split.
   - **Tests** (§11.2, `test_replay.py`):
     - Accepting a pending `SPLIT` makes `apply` propose, route, and apply a round-1 `LINK` for the tail, and the fake backend sees only that new event.
     - Rejecting a pending `LINK` offers the recorded alternative.

3. **High: stage 4 on a previously interpolated input.** **Accepted.** There are two parts.

   - **Refinement removes filled input rows** (§2.5). Every stage works on observed rows, and stage 4 fills gaps again from observed rows only. The old fills were computed for identities that refinement may change, so they are not preserved. The ledger header counts the removed rows.
   - **`interpolate_tracks_rts` is fixed for direct callers** (§6.4, change 1).
     - Rows flagged 1 (in `interp`, or `r3` in the positional layout) are excluded from the Kalman updates.
     - They are estimated again like any missing frame: filled with flag 1 where the gap rule allows, and dropped otherwise.
     - Raw tracker output never contains a 1, so its output and the existing tests are unchanged.
   - **Tests** (§11.4):
     - `test_interpolate.py`: `interp == 1` rows are not used as measurements, and a raw tracker file gives the same output as before.
     - `test_refiner.py`: filled input rows are removed and counted, and all output fills come from stage 4.

4. **High: protected occlusion gaps need an explicit interpolation API.** **Accepted.**

   - **New keyword** (§6.4, change 2): `interpolate_tracks_rts(..., protected_gaps: Mapping[int, Iterable[tuple[int, int]]] | None = None)`.
     - It gives, for each track, gaps as (last observed frame before, first observed frame after).
     - The track is cut into independent filter-and-smoother segments at each protected gap, so neither filling nor `smooth_existing` crosses it.
     - `None` keeps the current behavior.
   - **Where the gaps come from.** Stage 4 builds the map from the applied `LINK` events with `params.gate == "occluded"`. Each event's `params.gap` is placed under the final ID of its chain, and a chain with several such links contributes several gaps. Replay rebuilds the map from the same events.
   - **Tests** (`test_interpolate.py`):
     - a 63-frame protected gap stays empty with `max_gap=100`;
     - two protected gaps in one chain both stay empty;
     - smoothing does not cross a protected gap.

5. **Medium: link verification can strand a valid second choice.** **Accepted.**

   - **Re-assignment after rejection** (§6.3).
     - After each round, rejected edges (`AUTO_REJECT`, `VLM_REJECT`, `HUMAN_REJECT`) are removed.
     - Assignment re-runs on the affected components with margins recomputed, for up to `link.max_rounds` (3) rounds.
     - New pairs record `signals.replaces`.
   - **Pending edges.**
     - The endpoints of `HUMAN_PENDING` edges stay reserved, so a reviewer never sees competing links for one track end.
     - Each `LINK` records up to two alternatives in `signals.alternatives`, and the review card shows them.
     - If a reviewer rejects a pending edge, re-proposal (comment 2) re-runs the assignment without it.
   - **Tests** (`test_link.py`):
     - the three-tracklet fixture: i→j is rejected by the fake VLM, round 2 proposes i→k, and it is linked;
     - a pending edge keeps its endpoints reserved.

6. **Medium: the embedding cache can serve stale features.** **Accepted.**

   - **Full key** (§5.3):
     - the input track SHA-256;
     - the video's identity (SHA-256 of its first 64 MiB, file size, and frame count);
     - the context file's SHA-256;
     - encoder kind, model, and the weights' SHA-256;
     - `sample_every` and `occlusion_iou`;
     - crop preprocessing (padding, resize, normalization);
     - a `FEATURES_VERSION` constant.

     Any mismatch discards the cache.
   - **Occlusion mask.** It is computed from the raw input boxes and the context boxes only, so it depends on the inputs, not on decisions.
   - **Test:** `test_features_cache.py` checks that the cache is invalidated when the video, the context, the weights, a preprocessing setting, or `FEATURES_VERSION` changes, and reused otherwise.

7. **Medium: config validation contradicts the no-video mode.** **Accepted.**

   - **New `encoder.kind: none`** (§5.5, §9). It gives motion-only scoring. The VLM and evidence images still work when a video is given.
   - **Dependency checks are deferred** (§5.5, §9). A structurally wrong config still fails at load. Extras are checked at the start of `refine` or `apply`, and only for components the run will use:
     - the encoder's extra only with a video and a kind other than `none`;
     - the VLM backend's extra only with a non-`none` backend and a video.

     The error message suggests `encoder.kind: none`.
   - **Success criterion 1** now requires the no-video run on an installation without any `post-*` extra, using the default config.
   - **Test:** `test_minimal_install.py`, with the extras' imports made to fail:
     - the default config loads;
     - a run without video succeeds;
     - video with `dino` fails fast, naming the extra;
     - video with `none` succeeds.

8. **Medium: the ledger does not account for position edits.** **Accepted.**

   - **New position records** (§4.1, §6.4): `FILL` (one per filled gap) and `SMOOTH` (one per smoothed track).
     - They are always `AUTO_ACCEPT`, never sent to the VLM, and never shown in the review report.
     - `FILL` records the gap, `n_rows`, `gap_seconds`, `chord_h`, and `max_fill_speed_h_s`.
     - `SMOOTH` records `n_rows`, `mean_shift_px`, `max_shift_px`, and `max_shift_frame`.
     - Protected gaps get no `FILL`, because the occluded `LINK` already records them.
   - **Original positions are reconstructable.** `dnt-refine apply --no-fill` replays the ledger without stage 4 and reproduces the table as it was before filling and smoothing, including the original observed positions. Positions are not copied into the ledger.
   - **Audit.** The audit (§8.2) now samples `FILL` and `SMOOTH` records, with evidence images defined in §7.1, so interpolation and smoothing precision are measured.
   - **Goal (§1)** now states the split: identity and class edits are verified events, and position edits are deterministic records.
   - **Tests:**
     - `test_refiner.py`: one `FILL` per filled gap, and one `SMOOTH` per smoothed track;
     - `test_replay.py`: `--no-fill` reproduces the table as it was before filling.

## Additional fix found during revision

**An ambiguous link was auto-rejected instead of being sent to the VLM.** The routed score was `S_link · ramp(margin; 0 → 0.2)`. So a pair tied with its alternative (margin 0) was routed as 0 and auto-rejected. That contradicts the spec's own test, "two equally good candidates → routed to the VLM".

- **Replacement** (§4.3, §6.3): a pair with `margin < link.margin_min` (0.1) is capped at `link.ambiguous_cap` (0.75, below `accept_above`). It is never auto-accepted, and ambiguity alone never auto-rejects it.
- **Config and test.** New validation: `ambiguous_cap < link.accept_above`. The existing test is sharpened to check that the pair is neither auto-accepted nor auto-rejected.
