1. **High: a working `extra_kwargs["tracker_type"]` override was being removed.** **Accepted.** Response 3's claim was wrong for this key. The override is now **preserved**, so the compatibility claim holds and no versioning change is needed.

   **What I verified in 0.3.2.4** (`063a9b5`, `Tracker._build_boxmot_tracker`): `{"tracker_type": model.value}` was updated with `config.to_kwargs()`, so `extra_kwargs["tracker_type"]` replaced the tracker type. The signature filter then discarded every tuning field, and BoxMOT built the target from **its own** YAML defaults. Your example is right: `ByteTrackConfig(extra_kwargs={"tracker_type": "ocsort"})` ran OC-SORT with OC-SORT's defaults.

   The check also turned up a detail the translation has to reproduce. dnt filled in its default ReID weights based on the config's **own** `model`, never the override target. BoxMOT passes ReID arguments only to ReID targets.

   **Changes to the spec**
   - [§2.8](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#28-factory-level-keys-in-extra_kwargs-032x-compatibility): the `tracker_type` row now reads "Different: **preserved**". The new [§2.8.1](superpowers/specs/2026-09-23-dnt-0.3.3-correctness-packaging-design.md#281-tracker_type-override-preserved) sets out the translation:

     | Aspect | Translation in 0.3.3 |
     |---|---|
     | Target tracker | The override value, which must be one of the 8 `MOTModels` values (BoxMOT also rejected unknown types). §2.3 step 1 now uses the target throughout: which YAML is loaded, which allowlist applies, and what `create_tracker` receives. |
     | Base arguments | The **target's** YAML, or a passthrough `evolve_param_dict` / `tracker_config`. An untuned config with an override passes `create_tracker` exactly the 0.3.2.4 arguments. |
     | Source-class tuning fields | If all are `None`, which includes legacy-migrated untouched defaults, the result is identical to 0.3.2.4. Any non-`None` field raises `ValueError`, naming the target's config class. 0.3.2.4 silently discarded these fields, so this falls under the same silent-to-error policy as every other ignored setting. |
     | Tracker-parameter keys in `extra_kwargs` | Validated against the **target's** allowlist. |
     | `reid_weights` | Resolved by the exact 0.3.2.4 rule: the config's field, else the default only if the config's own `model` is a ReID tracker. It is passed only to ReID targets. |
     | `per_class`, `device`, `half` | Unchanged from the §2.8 table. |
     | Warning | `DeprecationWarning` pointing to the matching config class. The override is removed in 0.4. |

   - **One case is not guessed.** A non-ReID config aimed at a ReID target reaches BoxMOT with `reid_weights=None`, and what BoxMOT 16.0.11 does then depends on the target's own settings. The plan's first tasks run all 5 such cases on 0.3.2.4 in the reference environment:
     - a case that succeeds is reproduced identically and regression-tested
     - a case that fails never worked, so 0.3.3 raises a clear `ValueError` before reaching BoxMOT, with the 0.3.2.4 traceback stored as evidence

     A new §7 risk row covers this.
   - **Tests** (§2.6, factory-key group), including the regression test for the differing value that you asked for:
     - `ByteTrackConfig(extra_kwargs={"tracker_type": "ocsort"})` makes `create_tracker` receive `tracker_type="ocsort"` and the OC-SORT YAML snapshot. It builds an `OcSort` with OC-SORT's values and emits the warning.
     - The same config saved by **0.3.2.4**, as `passthrough/bytetrack_to_ocsort.yaml` and `.json`, gives the same result through `import_yaml` and `from_dict`.
     - `BoTSORTConfig(extra_kwargs={"tracker_type": "strongsort"})` carries its `reid_weights` over, following the 0.3.2.4 rule.
     - An override combined with a set source-class field raises `ValueError`.
     - An override combined with `evolve_param_dict` uses the dict as the base.
     - An unknown type raises `ValueError`.
     - The 5 non-ReID→ReID cases behave as recorded.
   - **Golden** (§5.3): OC-SORT tracks produced through `ByteTrackConfig(extra_kwargs={"tracker_type": "ocsort"})` must match 0.3.2.4 byte for byte.
   - **S3(a′)** now lists the `tracker_type` override among the preserved factory paths. The §6 changelog states that the override still works for untuned configs, is deprecated, and raises only when combined with source-class fields that 0.3.2.4 silently discarded.

   **Corrected claim:** with this change, every `extra_kwargs` path that affected 0.3.2.4's behaviour is preserved with identical results, and what changes is limited to values 0.3.2.4 silently ignored. That is the rule 0.3.3 applies everywhere as a patch release. The factory-level keys it covers are `evolve_param_dict`, `tracker_config`, `per_class`, ReID `reid_weights`, `tracker_type`, and `device` / `half` when the `Tracker` argument is `None`.
