## 1. [P1] One live event loop (Tasks 3, 4, 7)

Accepted. The review is right that the fake backends have no loop-bound connections, so they hid this.

- `VLMRunner` now starts one daemon thread with its own event loop on the first `ask_many` and keeps it until `close()`. `ask_many` submits with `asyncio.run_coroutine_threadsafe` and blocks. This works from plain code and from a thread that already runs a loop (Jupyter).
- Every backend has `async aclose()`, which closes its HTTP client. `close()` calls it on the loop that used the client, then stops the loop and joins the thread. `close()` is idempotent, and `ask_many` after `close()` raises `RuntimeError`.
- `refine` closes the runner in a `finally` around the stage run, so a failing run does not leak the thread or the connections.
- Tests:
  - A local `httpx` keep-alive server, with successive `ask_many` calls on one runner. Both return HTTP 200, and the test fails if the loop is closed between calls.
  - The same test from inside a running loop (the notebook path).
  - `test_backends_close_their_client_and_the_fake_counts_closes`.
  - `test_the_backend_is_closed_after_a_run_and_after_a_failing_one` in `test_vlm_refine.py`. It checks `FakeBackend.closed == 1` and that no `dnt-vlm-loop` thread is left, on success and when a stage raises after the loop has started.

## 2. [P1] Budget goes to whole questions in priority order (Task 4)

Accepted. I reproduced your case (`votes=3`, `max_calls=3`, `max_concurrency=2`): two questions each got part of the budget and neither completed.

- Admission now happens before anything is sent, in list order. The caller sorts the list by priority. Cached votes are free. A question is admitted only if **all its uncached votes** fit in what is left. Otherwise it gets `error="budget"` and no partial work is done. A later question that does fit (for example one with cached votes) is still admitted, so the budget is used fully while higher-priority questions always come first.
- **Retries are not billed against `max_calls`.** `calls` counts the votes sent, and a new counter `retries` counts the extra invocations. I chose this over reserving retry headroom for two reasons: a retry then can never take budget from another question, and the cost of a retry is bounded anyway (one invalid-reply retry, at most 3 transient attempts). The cost is that the real number of backend invocations can exceed `max_calls` by the number of retries. The spec follow-up in Task 9 records this.
- Tests, with concurrency greater than one:
  - Your exact case: the first question completes and the second gets `budget`.
  - Priority order with mixed cached and uncached votes.
  - Delayed retries do not consume another question's budget.
  - A tight budget with `max_concurrency=2`.

## 3. [P1] Cached answers are validated like fresh replies (Tasks 2, 4, 6)

Accepted. I reproduced the `NaN` confidence turning a pending SPLIT into `VLM_ACCEPT`.

- `AnswerCache.get(key, options=None)` treats an entry as a miss unless `answer` is a string (and in `options` when they are given) and `confidence` is a finite number in [0, 1], not a bool. The runner always passes the question's options.
- The runner also validates objects returned by a backend (`_check`), so a custom backend cannot return garbage either.
- `interpret` and `_pending_reason` never accept on a non-finite confidence, as a second line of defence.
- Tests:
  - `test_readable_but_invalid_entries_are_misses`, with 10 malformed entries (NaN, inf, negative, above 1, bool, string, `None`, missing key, answer outside the options, non-string answer).
  - The good-entry counterpart.
  - `test_a_non_finite_confidence_never_accepts_an_edit`.
  - `test_a_damaged_cache_entry_cannot_accept_an_edit`, which goes through the routing with the damaged entry on disk and asserts zero accepted edits.

## 7. [P1] Review images are deleted only when the report owns them (Task 8)

Accepted. I reproduced the loss of `my-photo.jpg`.

- `write_review` writes `OUT.review/manifest.json` with the exact image names it created. It deletes only names listed in a manifest. Names must be plain file names ending in `.jpg`, so a manifest cannot point outside the directory.
- With no manifest, nothing but the page is removed. On a rerun, images that the previous manifest listed and the new run does not need are removed. A manifest is never started in a directory the report did not create. The directory itself is removed only when it is empty.
- `check_output_paths` now also rejects an input file that lives inside `OUT.review/` (with a clear message), because a generated image or the manifest could overwrite it.
- Tests:
  - `keep.jpg` and `keep.txt` survive.
  - No manifest means no deletion.
  - A rerun replaces only the images it owns.
  - A manifest with `../precious.jpg` and an absolute path deletes nothing.
  - The directory is removed when nothing of the user's lives there.
  - The input-collision guard.

## 8. [P1] Saved choices are bound to the proposal (Task 8, 7)

Accepted.

- `refine` computes a `run_key`: a SHA-256 of the track-file hash, context hash, video fingerprint, reclass-hint hash and the full config. It goes on the page as `data-run`, and the localStorage key is `dnt-refine-review:<run_key>`, no longer the title.
- Each saved choice records the card's `proposal_key`. A choice is restored only when the stored key equals the card's `data-key`. A mismatch, a choice other than accept/reject, a missing key, or an absent store restores nothing.
- The pure functions (`storageKey`, `restorable`, `exportDecisions`) live in `_JS_PURE`, apart from the DOM code. The tests run them under `node`: the namespacing, the key check against a different proposal with the same id, and the `decisions.json` format from spec §4.2. They are skipped if `node` is not installed (it is here, v22). The DOM wiring itself has no browser test.
- Python tests: `data-key` and `data-run` are in the page; regenerating with the same event id and a different `proposal_key` gives a different card key. An end-to-end test regenerates `o.review.html` from another track file with the same event id `switch-r0-000001` and asserts that both the run key and the card key changed.
