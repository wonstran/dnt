The response resolves the six comments from the previous review in the written design. These additional cases need decisions before implementation.

## Comments

1. **[High] Freeze accepted links when reassignment runs.** Section 6.3 says rejected edges are removed and assignment reruns on the affected component (design lines 599–609), but reserves endpoints only for `HUMAN_PENDING` edges. If a component has one accepted pair and one rejected pair, a fresh Hungarian solution can assign an endpoint from the accepted pair to a different partner. The ledger would then contain incompatible accepted links, or silently replace a verified edit. Remove endpoints of accepted pairs from later assignment rounds and keep those pairs fixed; test a component where rejecting one edge changes the unconstrained optimum for an already accepted edge.

2. **[High] The orphan pass can auto-drop a fragment while its link is pending.** Pending link endpoints remain reserved during stage 3 (design line 608), yet the orphan rule drops any short track with *no accepted link* (lines 539–547). A 0.1-second fragment with a `HUMAN_PENDING` link scores 1.0 for `DROP{orphan}` and is removed before the reviewer decides whether to link it. Exclude endpoints of pending links from automatic orphan deletion, or make the orphan decision conditional on the link decision. Add an end-to-end test for a short fragment with a pending link.

3. **[High] Replay without the video needs a rule for a missing embedding cache.** The response allows a missing recorded video because embeddings come from the cache (response lines 25–34; design lines 298–322). But `OUT.features.npz` is an output cache, not a verified replay input, and may be absent or incomplete. Re-proposing switch or scored-link events then needs appearance features that cannot be computed; the current rule only addresses missing *evidence images*. Require a complete, validated cache before permitting video-free re-proposal, or fail with an actionable error. Test `apply` after both the recorded video and feature cache are unavailable.

4. **[Medium] State explicitly that pending events are serialized.** The ledger says an event line is written when its decision is *final* (design line 289), while `HUMAN_PENDING` events need ledger IDs so the review page can export decisions and `apply` can resolve them (lines 305–313, 750–760). If “final” excludes pending, this workflow cannot work. Say that every proposed event, including `HUMAN_PENDING`, is written with its current decision, then append or produce a new ledger for later review rounds. Test a pending event's ledger round trip and subsequent decision override.

This is a static review of the response and design. No implementation tests were run.
