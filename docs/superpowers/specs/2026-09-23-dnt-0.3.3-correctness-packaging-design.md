## 0. Context and agreed constraints

The dnt upgrade is split into six sub-projects, each with its own spec, plan, and implementation cycle:

| Sub-project | Scope |
|---|---|
| **A** | **0.3.3 correctness and packaging (this spec)** |
| B | Internal foundations |
| C | Dependency migration (BoxMOT 25, new Ultralytics) |
| D | Speed |
| E | Unified public API and tuning |
| F | New capabilities |

Constraints agreed during brainstorming:

1. **dnt has outside users who install it from PyPI.** Changes follow semantic versioning. 0.3.3 is a patch release, so the public API does not change. The only exception is that silent misbehaviour becomes a clear error. Detection and track files written by 0.3.x must keep loading.
2. **Tracker settings bug (B1).** User-set tracker settings must take effect. A setting that cannot affect the chosen tracker is rejected with a clear error; it is never accepted silently. Saved 0.3.2.x configs migrate by an explicit rule (§2.7), so an untouched old export keeps its untuned results. Users who never tuned anything must get **byte-identical** tracks, because the effective defaults stay BoxMOT's YAML defaults. This guarantee applies within the recorded reference environment defined in §5.1.
3. **B1 mechanism.** Overlay the user's settings on BoxMOT's own YAML defaults and pass the result as `evolve_param_dict`. Do not construct tracker classes directly in 0.3.3.
4. **Test data.** CI uses a synthetic video with a stub detector. Golden-file and benchmark tests use a local clip given by `DNT_REF_CLIP`, and the clip stays out of git.
5. **Environment-visible cleanups ship in 0.3.3:** removing unused dependencies, `requires-python >=3.11`, and removing the `sys.path` hacks.

## 2. B1: tracker settings reach BoxMOT (also B2 and the Tracker part of B8)

### 2.1 Root cause (verified against the BoxMOT 16.0.11 source)

`Tracker` filters its kwargs down to `signature(create_tracker)`, which is `(tracker_type, tracker_config, reid_weights, device, half, per_class, evolve_param_dict)`. That discards every tuning field. When `evolve_param_dict is None`, `create_tracker` loads `configs/trackers/<type>.yaml` and uses `{k: v["default"]}`. Otherwise it uses `evolve_param_dict.copy()` in its place. Either way, the resulting dict is passed as `tracker_class(**tracker_args)`.

All BoxMOT 16 tracker classes accept `**kwargs` and forward them to `BaseTracker(det_thresh, max_age, max_obs, min_hits, iou_threshold, per_class, nr_classes, asso_func, is_obb, **kwargs)`. `BaseTracker` also accepts `**kwargs`. As a result, **unknown names are ignored silently**, so dnt must validate them itself.

### 2.2 Config classes

- Every config becomes `@dataclass(kw_only=True)`: `MOTBaseConfig` and the 8 subclasses. Positional use (for example `BoTSORTConfig(ReIDWeights.X)`) now raises `TypeError`. **This fixes B2.**
- Every tuning field defaults to `None`, meaning "use BoxMOT's default". Each docstring states the effective value, for example "`track_thresh`: default `None` (BoxMOT 16: 0.6)".
- `model`, `per_class`, `reid_weights`, and `extra_kwargs` keep their current meaning and defaults.
- `from_dict`, `to_dict`, `export_yaml`, and `import_yaml` still work. YAML exported by 0.3.2.x keeps loading through an explicit migration rule (§2.7), so an untouched old export still gives untuned results.

Fields and their effective defaults (BoxMOT 16 YAML):

| Config | Existing fields | Added fields |
|---|---|---|
| `ByteTrackConfig` | `track_thresh` (0.6), `match_thresh` (0.9), `track_buffer` (30), `frame_rate` (30) | `min_conf` (0.1) |
| `BoTSORTConfig` | `track_high_thresh` (0.6), `track_low_thresh` (0.1), `new_track_thresh` (0.7), `match_thresh` (0.8), `track_buffer` (30), `proximity_thresh` (0.5), `appearance_thresh` (0.25), `with_reid` (constructor default) | `cmc_method` ("ecc"), `frame_rate` (constructor default) |
| `OCSORTConfig` | `det_thresh` (0.6), `max_age` (30), `min_hits` (3), `iou_threshold` (BaseTracker default), `asso_func` ("iou"), `delta_t` (3), `inertia` (0.1) | – |
| `DeepOCSORTConfig` | `det_thresh` (0.5), `max_age` (30), `min_hits` (3), `iou_threshold` (BaseTracker default), `asso_func` ("iou"), `delta_t` (3), `inertia` (0.2) | – |
| `StrongSORTConfig` | `max_dist` → **renamed** `max_cos_dist` (0.4), `max_iou_dist` (0.7), `max_age` (30), `n_init` (3), `nn_budget` (100), `ema_alpha` (0.9), `mc_lambda` (0.98) | – |
| `HybridSORTConfig` | `det_thresh`, `max_age`, `min_hits`, `iou_threshold`, `asso_func` (BaseTracker defaults) | – |

| `SFSORTConfig` | `det_thresh`, `max_age`, `min_hits`, `iou_threshold`, `asso_func`: **all non-effective** (see below) | `high_th` (0.6), `low_th` (0.1), `new_track_th` (0.7), `match_th_first` (0.67), `match_th_second` (0.3) |

"Constructor default" and "BaseTracker default" mean the key is not in BoxMOT's YAML, so the class signature default applies. That is exactly what happens today.

`StrongSORTConfig.max_dist` is still accepted as a deprecated alias. It emits `DeprecationWarning` and maps to `max_cos_dist`. Setting both raises `ValueError`.

#### Effective parameters and non-effective fields

A field is **effective** for a tracker only if BoxMOT 16.0.11's code for that tracker reads it after construction, and the value it reads is the value the user supplied. Acceptance by `__init__` or `**kwargs` does not count, and neither does the value appearing as an attribute on the constructed object. Each tracker has an allowlist, `EFFECTIVE_PARAMS[tracker]`, which lists exactly the fields that dnt exposes for that tracker and has shown to be effective. `extra_kwargs` keys are validated against the same allowlist. It stops being a way to pass unverified BoxMOT arguments; that escape hatch returns in 0.4, with the same evidence requirement for anything added.

"Shown" requires both of the following:

1. **Source evidence.** For every allowlisted field, [Appendix A](#appendix-a-source-evidence-for-effective-parameters) records the file and line in the 16.0.11 source where the tracker reads the value after construction. The same evidence is committed as `tests/data/boxmot_16.0.11_param_evidence.json`, one entry per tracker and field, holding `{file, line, code}`.
2. **Behaviour evidence**, wherever the synthetic scenario can show it (§2.6). A test that would fail if the field were a no-op.

Fields that come from the `BaseTracker` base class need the most care, so they are audited separately:

| Tracker | BaseTracker fields it reads (evidence in Appendix A) | BaseTracker fields exposed by dnt but **not** read |
|---|---|---|
| ByteTrack | `det_thresh` (set from `track_thresh`) | (none exposed) |
| BoT-SORT | none | (none exposed) |
| OC-SORT | `det_thresh`, `max_age`, `min_hits`, `iou_threshold` (as `asso_threshold`), `asso_func` | – |
| Deep OC-SORT | `det_thresh`, `max_age`, `min_hits`, `iou_threshold`, `asso_func` | – |
| StrongSORT | `max_age` | – |
| HybridSORT | `det_thresh`, `max_age`, `min_hits`, `iou_threshold`, `asso_func` (via `asso_func_name`) | – |
| BoostTrack | `det_thresh`, `max_age`, `min_hits`, `iou_threshold` | `asso_func` |
| SF-SORT | none | `det_thresh`, `max_age`, `min_hits`, `iou_threshold`, `asso_func` |

Notes on the SF-SORT row:
- `SFSORT.__init__` sets `det_thresh` itself from `high_th` and passes it to `BaseTracker`. A user-supplied `det_thresh` would therefore raise a duplicate-keyword `TypeError` inside BoxMOT.
- `max_age` only changes `BaseTracker.max_obs`, which SF-SORT never reads.
- `asso_func` only builds an association function that SF-SORT never calls.
- BoostTrack's `asso_func` appears only in its docstring.

**Silent clamping (SF-SORT).** SF-SORT passes its settings through `_resolve_or_default(value, default, lo, hi)`, which **clamps** them without any warning (`sfsort.py:336-340`). A value outside the range becomes a different value. dnt therefore checks these ranges and raises `ValueError` rather than letting BoxMOT change the value:

| Field | Allowed range |
|---|---|
| `high_th` | [0, 1] |
| `match_th_first` | [0, 0.67] |
| `new_track_th` | [`high_th`, 1] |
| `low_th` | [0, `high_th`] |
| `match_th_second` | [0, 1] |

When `high_th` is not set, the range checks use BoxMOT's effective `high_th`. Any other tracker that turns out to clamp during the plan's line-by-line re-check gets the same treatment.

**Rule for non-effective fields in direct use.** 0.3.3 is a patch release, so non-effective fields stay on the dataclasses; removing them would break code that passes them.
- Setting one to any non-`None` value, whether in the constructor, by attribute, in `extra_kwargs`, or through `from_dict`, raises `ValueError` when the tracker is built. For example: `SFSORTConfig: 'det_thresh' has no effect on SF-SORT in BoxMOT 16; use 'high_th' for the detection threshold.`
- Each field has one mapped hint:

  | Field | Hint |
  |---|---|
  | `det_thresh` | use `high_th` |
  | `max_age` | use `marginal_timeout` / `central_timeout` |
  | `min_hits`, `iou_threshold`, `asso_func` | no equivalent for this tracker; remove the argument |

- Saved 0.3.2.x files are the only input that is migrated rather than rejected. They are recognised explicitly, and never guessed from a plain dict (§2.7).
- The fields are removed in 0.4.

With these rules, no exposed setting is accepted silently without effect. Values outside the allowed range are rejected rather than silently clamped.

### 2.3 Building the tracker arguments

A new private function `_build_tracker_args(config) -> dict` in `track/tracker.py`:

1. `tracker_type = config.model.value`. Load BoxMOT's YAML defaults with the same code path BoxMOT uses: `get_tracker_config(tracker_type)` followed by `{k: v["default"]}`.
2. Collect the user values: the non-`None` tuning fields from `asdict(config)` (excluding `model`, `per_class`, `reid_weights`, and `extra_kwargs`), plus `extra_kwargs`. Then apply the renames (`max_dist`→`max_cos_dist`).
3. **Validate** each user key, whether it comes from a dataclass field or from `extra_kwargs`, against `EFFECTIVE_PARAMS[tracker_type]` (§2.2). This is a module constant in dnt, keyed to the pinned BoxMOT 16.0.11.
   - A known non-effective field raises `ValueError` with its mapped hint.
   - A value outside a clamped range (SF-SORT, §2.2) raises `ValueError` naming the range.
   - Any other key outside the allowlist raises `ValueError(f"{Config.__name__}: '{k}' is not an effective BoxMOT parameter for {tracker_type}. Valid: {sorted(allowed)}")`.
   - Keys that come from BoxMOT's own YAML are **not** validated and are passed through unchanged, which keeps untuned behaviour identical.
   - Whether each allowlisted field is effective is established by the evidence and behaviour tests in §2.6, not by constructor signatures.
4. Return `{**yaml_defaults, **user_values}`.

`Tracker` then calls `create_tracker(tracker_type=..., reid_weights=..., device=..., half=..., per_class=config.per_class, evolve_param_dict=_build_tracker_args(config))`. The current signature-filtering logic and the import-path fallback chain (`tracker_zoo` variants) are both replaced. The package requires `boxmot==16.0.11` (§4.1), and `from boxmot import create_tracker` is the supported path in that version.

### 2.4 `update()` call

Remove the `except TypeError: tracker.update(dets, frame, None)` retry. A real `TypeError` raised inside `update` must propagate instead of re-running `update`.

### 2.5 Device and precision (the Tracker part of B8)

Extract the Detector's resolution logic (validate `{auto, cuda, xpu, mps, cpu}` with an optional `:N`; `auto` resolves as cuda → xpu → mps → cpu; an unavailable backend falls back to cpu) into the private `dnt/_device.py` as `resolve_device(device: str) -> str` and `half_allowed(device: str, half: bool) -> bool`. `half_allowed` is true only when the resolved device starts with `"cuda"`. `Detector`, `Segmentor`, and `Tracker` all call it.

`Tracker` then converts the resolved device to BoxMOT's format (`"cuda:N"` → `"N"`, `"cpu"` → `"cpu"`, `mps` passed through). The `CUDA_VISIBLE_DEVICES == "auto"` workaround is removed.

### 2.6 Tests (S2, S3)

The tests are parametrised over all 8 trackers. ReID trackers use the committed `osnet_x1_0_msmt17.pt` on the CPU, so nothing is downloaded. The tests fall into four groups, and each group proves something different. Only groups 2 and 3 are evidence of **effectiveness**.

1. **Propagation tests.** These show only that dnt passes the value on. They are not evidence of effect.
   - For each tracker, set two non-default effective values and assert that they reach `create_tracker`'s `evolve_param_dict` and the constructed object.
   - An untuned config gives `_build_tracker_args(cfg) ==` the stored snapshot `tests/data/boxmot_16.0.11_yaml_defaults.json`, which holds the eight 16.0.11 YAML default dicts.
   - The installed BoxMOT's YAML equals that snapshot. On mismatch the test fails and names the installed version.
2. **Source-evidence tests.**
   - `EFFECTIVE_PARAMS` equals the key set of `tests/data/boxmot_16.0.11_param_evidence.json`, so every allowlisted field has evidence and every evidence entry is allowlisted.
   - For each entry, the recorded `code` string appears at the recorded `file:line` in the **installed** BoxMOT source, located with `importlib.util.find_spec("boxmot")`. That keeps the evidence tied to real code rather than a hand-written table. With the exact pin it cannot drift silently.
3. **Behaviour tests.** Each test fails if the field is a no-op. It runs the tracker on the synthetic scenario (§5.2) twice: once with the snapshot default, and once with a **probe value**. It then asserts the stated observable difference. Required probes:

   | Field family | Trackers (field) | Probe → expected observable |
   |---|---|---|
   | Detection threshold | ByteTrack (`track_thresh`), BoT-SORT (`track_high_thresh`, `new_track_thresh`), OC-SORT, Deep OC-SORT, HybridSORT, BoostTrack (`det_thresh`), SF-SORT (`high_th`, `new_track_th`) | Set above the stub confidence 0.9 → **no tracks**; the default gives 3 tracks |
   | Low-score band | ByteTrack (`min_conf`), BoT-SORT (`track_low_thresh`), SF-SORT (`low_th`) | Stub confidence split into 0.9 and 0.3 halves, with the high threshold at 0.5 → low band on gives more rows than low band off |
   | Track lifetime | ByteTrack, BoT-SORT (`track_buffer`), OC-SORT, Deep OC-SORT, HybridSORT, BoostTrack, StrongSORT (`max_age`) | Set to 2 (below the 8-frame gap) → object 1 gets a **new ID** after frame 67; the default keeps one ID |
   | Confirmation | OC-SORT, Deep OC-SORT, HybridSORT, BoostTrack (`min_hits`), StrongSORT (`n_init`) | Set to 20 → output rows for frames 1–19 disappear |
   | Match threshold | ByteTrack, BoT-SORT (`match_thresh`), SF-SORT (`match_th_first`, `match_th_second`), OC-SORT, Deep OC-SORT, HybridSORT, BoostTrack (`iou_threshold`) | Set to an extreme value (near-zero matching allowance, or IoU ≥ 0.99) → **ID count increases** on the crossing and noisy frames |

   The plan works out the concrete probe values and asserts them. A probe that cannot produce its stated difference on the synthetic scenario may be moved, with a written reason, to the **evidence-only list** below. That list is part of what the maintainer reviews in the plan.
4. **Evidence-only fields.** These are fields whose effect needs appearance features or camera motion that the synthetic scenario doesn't produce, or that change results only subtly: `appearance_thresh`, `proximity_thresh`, `with_reid`, `cmc_method`, `frame_rate`, `asso_func`, `delta_t`, `inertia`, `max_iou_dist`, `max_cos_dist`, `nn_budget`, `ema_alpha`, `mc_lambda`. For these, the spec claims only **source evidence** (group 2), and the docs make no stronger claim.

**Validation tests:**
- Every non-effective field in §2.2 raises `ValueError` with its hint, through each of these paths: the constructor, attribute assignment, `extra_kwargs`, and `from_dict`.
- SF-SORT range violations raise `ValueError`, including the relative bounds (`new_track_th < high_th`, `low_th > high_th`).
- An unknown field raises `ValueError`.
- Positional arguments raise `TypeError`.
- `max_dist` emits a warning and maps to `max_cos_dist`. Setting both raises.

**Saved-config tests** (§2.7):
- **Legacy files:** the eight 0.3.2.4-exported default files are stored in `tests/data/legacy_0.3.2/`, generated once by running 0.3.2.4's `export_config_to_yaml(config=XConfig())` in the baseline environment. Each one imports with `legacy="auto"` to `_build_tracker_args ==` the YAML snapshot, which is the untuned result.
- **Edited legacy files:** a legacy file with one edited effective value applies that value. One with an edited non-effective value raises `ValueError`.
- **New-format files** and **plain dicts** with the same content go down the strict path.
- `legacy=True` on a file that is not legacy-shaped raises `ValueError`.

### 2.7 Saved configs: format version and 0.3.2.x migration

**The problem.** In 0.3.2.x, `export_yaml` and `export_config_to_yaml` wrote **every** dataclass field (`model`, `per_class`, `extra_kwargs`, `reid_weights` where present, and all tuning fields) as a flat mapping with dnt's old defaults. That happened even when the user tuned nothing. BoxMOT ignored all of those values (B1). If 0.3.3 treated them as user-set, untuned saved configs would suddenly apply the old dnt defaults and change results. For example, `ByteTrackConfig()` exported `track_thresh: 0.5, match_thresh: 0.8`, while BoxMOT's effective values are 0.6 and 0.9. A plain dict carries no record of where it came from, so it can't be told apart from new user input by inspection.

**Format version.** Files exported by 0.3.3 start with `dnt_config_version: 2`. Such a file is **new input**, and loading it follows the strict rules in §2.2–2.3. The version key is file metadata. Loaders remove it before parsing fields, so it is never validated as a tracker setting. `to_dict()` keeps returning fields only; the export functions add the key. A file with an unknown version (anything other than 2) raises `ValueError`.

**Legacy detection.** `import_yaml(path, legacy="auto")`, `Tracker.import_config_from_yaml(path, legacy="auto")` and `Tracker(config_yaml=path)` treat a file as a **0.3.2.x export** only when both of these hold:
1. it has no `dnt_config_version` key, and
2. its key set is **exactly** the 0.3.2.4 field set of the config class named by its `model`. That field set is taken from `063a9b5` and stored as `LEGACY_0324_FIELDS`.

Only 0.3.2.x's export functions produce that exact shape. A hand-written partial file has no version key but has a different key set, so it is strict.
- `legacy=True` forces migration, and raises `ValueError` if the file is not legacy-shaped.
- `legacy=False` forces the strict path.
- **`from_dict(data)` is always strict.** Migrating a dict must be requested explicitly with `MOTBaseConfig.from_legacy_dict(data)`, which applies the same shape check.

**Migration rule** for a detected or requested legacy mapping. Each tuning field is compared with the **0.3.2.4 dnt default** for that class (`LEGACY_0324_DEFAULTS`, stored as a snapshot and checked against `git show 063a9b5`):

| Legacy value | Field is effective | Field is non-effective |
|---|---|---|
| Equals the 0.3.2.4 default | Migrated to `None` (BoxMOT default), since the user never set it and 0.3.2.x never applied it | Dropped |
| Differs from the 0.3.2.4 default | Kept as user-set, so it now takes effect (the B1 fix) | `ValueError` with the §2.2 hint, since the user asked for a setting that can't take effect |

- `model`, `per_class` and `reid_weights` load unchanged. 0.3.2.x did pass these to BoxMOT.
- `max_dist` maps to `max_cos_dist`.
- A legacy load emits **one** `DeprecationWarning` that:
  - names the file
  - lists the fields migrated to BoxMOT defaults and the fields kept as user-set
  - says to re-export the config (which writes `dnt_config_version: 2`) or to set values explicitly

**Stated limitation.** In a legacy file, a value that the user deliberately set **equal to** the old dnt default can't be told apart from an untouched default, so it migrates to the BoxMOT default. The warning names every such field so the user can set it again explicitly. The changelog states this limitation.

**Result.** An untouched 0.3.2.x export gives byte-identical tracks. A tuned 0.3.2.x export applies the user's changed values, as agreed for B1. New files and plain dicts are strict, so an intentional non-effective setting always produces an error.

### 3.1 Synchronizer timeline (B12)

**Current behaviour** (0.3.2.4):
- `add_unix_time` computes `unix_time(f) = round(ref_time + (f − ref_frame) · 1000/fps)`.
- `ref_time` means the wall-clock time **at** `ref_frame` of the first video.
- For each later video, `process()` resets `ref_frame` to 0 but never advances `ref_time`, so every later video restarts at the first video's reference time.
- `offsets` is length-checked and then ignored.

**Definitions.** For videos *i* = 0 … *k*−1, let:
- *n*ᵢ be the frame count (`Detector.get_frames`)
- *p*ᵢ = 1000 / fpsᵢ, the milliseconds per frame
- *o*ᵢ = `offsets[i]`, an integer number of frames of video *i*, default 0. **`offsets[0]` must be 0** (see below).
- *R* = `ref_time` in ms, and *r* = `ref_frame`, a frame index **in video 0**.

**Formula.** *T*ᵢ(*f*) is the unrounded time of frame *f* of video *i*.

- Video 0: *T*₀(*f*) = *R* + (*f* − *r*) · *p*₀. So *T*₀(*r*) = *R* exactly: `ref_time` is always the time at `ref_frame`.
- Video *i* ≥ 1: *T*ᵢ(*f*) = *E*ᵢ₋₁ + (*f* + *o*ᵢ) · *p*ᵢ
- where *E*ᵢ₋₁ = *T*ᵢ₋₁(*n*ᵢ₋₁) is the time one frame after the last frame of video *i*−1, which is where the next video starts when there is no gap.
- Output: `unix_time = round(Tᵢ(f))` as int64 ms. Rounding happens **only at output**. *E*ᵢ is carried unrounded, so rounding errors do not build up across a long list of videos.

**Meaning of offsets.**
- *o*ᵢ > 0 inserts a gap of *o*ᵢ frames (at video *i*'s frame rate) before video *i* starts.
- *o*ᵢ < 0 makes video *i* overlap the end of the previous video by |*o*ᵢ| frames.
- **`offsets[0]` has no meaning.** Video 0 has no previous video to be offset from, and its placement is fully fixed by `ref_frame` and `ref_time`. A non-zero `offsets[0]` therefore raises `ValueError("offsets[0] must be 0; position video 0 with ref_frame/ref_time")`. This matches the patch-release policy that silent behaviour becomes an explicit error: 0.3.2.4 ignored every offset. The entry stays in the list so that `offsets[i]` lines up with `videos[i]`.
- Offsets are relative to the previous video's end, not cumulative from video 0.

**Worked example** (this is also the unit test):
- Inputs: video 0 has 100 frames at 25 fps, *r* = 25, *R* = 1 000 000 ms. Video 1 has 30 fps.
- Offsets `[0, 0]`:
  - *T*₀(25) = 1 000 000
  - *T*₀(99) = 1 002 960
  - *E*₀ = *R* + (100 − 25) · 40 = 1 003 000, so video 1 starts **3 s** after `ref_time`, not 4 s
  - *T*₁(0) = 1 003 000
- Offsets `[0, 5]`:
  - *T*₁(0) = 1 003 000 + 5 · 33.333… = 1 003 166.67, which outputs as 1 003 167
- Offsets `[2, 0]`: raises `ValueError`, because `offsets[0]` must be 0.
- Negative offset `[0, −3]`:
  - *T*₁(0) = 1 003 000 − 100 = 1 002 900, overlapping video 0's last 2.5 frames

**Behaviour kept from 0.3.2.4:**
- the video 0 formula when `offsets` is `None` or all zeros (byte-identical output for single-video use)
- the output columns
- the `ValueError` checks on fps and length

A non-integer offset raises `ValueError`, and so does a non-zero `offsets[0]`.

**Public docstring.** The `Synchronizer` docstring for `offsets` becomes:

> *offsets*: optional list of integers, one per video, in frames of that video. `offsets[0]` must be 0, because video 0 is placed by `ref_frame` and `ref_time`, and `ref_time` is the wall-clock time at `ref_frame` of video 0. For *i* ≥ 1, video *i* starts `offsets[i]` frames after the end of video *i*−1. Positive values add a gap and negative values add an overlap. Offsets are relative to the previous video, not cumulative.

### 5.1 Reference environment (the scope of the byte-identical guarantee)

The byte-identical guarantee in S3(b) holds only when both versions run in one **recorded** environment. That environment is fixed as follows:

- **Lock file.** `tests/golden/reference-env.txt` is a fully pinned `uv pip compile` output with hashes, for Python 3.12, covering every transitive dependency. The key pins are the versions dnt last ran with:
  - `torch==2.10.0`, `torchvision==0.25.0`
  - `ultralytics==8.4.14`, `boxmot==16.0.11`
  - `numpy==2.4.2`, `pandas==2.3.3`
  - `opencv-python==4.13.0.92`
  - `scipy==1.17.0`, `filterpy==1.4.5`

  The torch build tag (CPU or CUDA version) is recorded on the lock file's first line.
- **Baseline environment.** Create a git worktree of `063a9b5` (0.3.2.4). Install the lock file with `uv pip sync tests/golden/reference-env.txt`, then install dnt with `uv pip install --no-deps -e <worktree>`. The `--no-deps` flag matters: 0.3.2.4's own metadata has no BoxMOT upper bound, and it must not be allowed to resolve a newer, incompatible BoxMOT.
- **Comparison environment.** A separate venv set up the same way from the same lock file, with dnt 0.3.3 installed using `--no-deps -e .`.
- **Environment check.** Both runs record `importlib.metadata` versions for every package in the lock file into the golden manifest (`manifest.json`), together with the Python version, the torch build, the GPU name, and the driver version. `make_golden.py` refuses to write, and the golden tests refuse to compare, if either environment's versions differ from the lock file. The failure message names the differing packages.
- **Determinism.**
  - **Tracking** golden runs for all trackers use `device="cpu"` and `half=False`. That removes GPU non-determinism, including in ReID, from the tracking comparison.
  - **Detection** golden runs use the maintainer's GPU at FP32, and the GPU name is recorded. If two consecutive baseline runs of detection differ, the manifest records `detect_deterministic: false`, and detection is then compared at a documented tolerance (x/y/w/h ±1 px, conf ±0.01, identical row count). Tracking is unaffected, because it consumes the **stored** baseline detection file, not freshly generated detections.
- **What the guarantee says.** The changelog states it exactly: *"With the dependency versions in `tests/golden/reference-env.txt`, untuned tracks are unchanged from 0.3.2.4."* The version-independent guarantee is S3(a): identical arguments reach BoxMOT 16.0.11, whose version is pinned.

1. **Pre-flight checks**, before any tracker runs. `make_golden.py` aborts, and writes nothing, if any of these fails:
   - the environment check (§5.1)
   - `DNT_REF_CLIP` opens, and its frame count and fps are positive; its SHA-256 is recorded
   - the baseline detection file is non-empty and has the `DET_FIELDS` layout
   - `osnet_x1_0_msmt17.pt` exists and matches its committed SHA-256
   - the output directory is writable
2. **Any exception from a tracker aborts the run** (non-zero exit, and no partial manifest), **unless** it matches an entry in `tests/golden/known_baseline_defects.yaml`. Each entry records:
   - `tracker`
   - `exception_type`, which must match exactly
   - `message_regex`, which must fully match the message
   - `raised_at`, the innermost frame's `file:function` within dnt or BoxMOT, which must match
   - `root_cause`, a written explanation of the 0.3.2.4 defect, with a code reference
   - `reviewed_by` and `reviewed_on`
   - `evidence`, the path to the stored traceback
3. **Where entries come from.** The file starts **empty**. An entry is added only in a separate commit that the maintainer reviews, after a failed baseline run has been diagnosed as a genuine 0.3.2.4 defect. It must not be caused by the environment, data, or weights. `make_golden.py` never writes to this file.
4. **Exempted trackers.** For a tracker exempted this way, the manifest records `{"tracker": ..., "status": "known_defect", "defect_id": ..., "traceback_sha256": ...}`. The comparison test then asserts that 0.3.3 completes without error and produces the track schema, and it prints the exemption. The changelog names the tracker and the defect.
5. **Everything else** must match **byte for byte**: every tracker without such an entry, plus the interpolate and link outputs. If a known-defect entry no longer reproduces on the baseline (the tracker now succeeds, or it fails differently), golden generation also aborts, so stale exemptions can't linger.

The reference clip should be at most about 60 s, so that eight CPU tracking runs, five of them with ReID, stay practical. Its duration and hash are recorded in the manifest.
