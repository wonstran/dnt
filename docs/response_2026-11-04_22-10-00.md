Both findings are correct and are accepted. Rev. 3 read the side of a cut from the rows a track still holds, and that was the wrong basis: dedup can legitimately remove all of those rows. The claim in success criterion 4 that this held "after dedup has edited either side" was not true in rev. 3.

## Changes

| Comment | Resolution | Where |
|---|---|---|
| **[P1]** Keep side membership when dedup replaces a side's rows | **Side tags** replace the lineage predicate `straddles`. A tag `(r, k)` means side `k` of raw ID `r`'s cuts. A track's tags are `own(t)`, read from its current lineage, plus `carried[t]`, the tags of every track merged into it. `ReversalSides`, which `_Stages` owns, holds the cuts and `carried`. Dedup computes every track's tags before it applies merges, refuses a join whose component tags conflict (`blocker` reason `"reversal"`), and afterwards passes the absorbed tracks' tags to their representatives. So a side survives even when none of its rows do. Link's merges carry tags the same way. Link's pair check and chain check use the tags. Tags are never written into lineage, so proposal keys, evidence and ledger lineage keep their observed-row meaning, as you asked. Your replacement case is a test run through dedup and then link with `link.normal_heading_check = False`. It must fail without `reversal_sides` (link accepts `[1, 2]` at 0.975) and must give no `[1, 2]` candidate with them. Unit tests cover deriving tags with several cuts, the order of `side_conflict`, and composing `absorb` over a dedup map followed by a link map. | §2, §3.4, §3.5, §6.2, success criterion 4 |
| **[P2]** Find the chain path by graph traversal | `resolve_reversal_chains` now works on the graph:<br>1. Build an undirected graph of the active links; its components are the chains.<br>2. Visit components in order of their smallest member ID, and stop at the first whose tags conflict.<br>3. Pick `u` and `v` as the smallest member IDs holding each of the two sides.<br>4. Find the `u`–`v` path by breadth-first search, with neighbours in ID order. If two links join the same pair, the weaker one counts.<br>5. Drop the weakest event on that path by `(algo_score, proposal_key)`, then repeat.<br><br>Each round removes one link, so it ends, and links off the path are never dropped. Your chain whose path is not in first-frame order (`A` 0–28, `X` 30–31, `Y` 29–32, `B` 33–60, cut raw 10 at 32) is a test. It checks that `resolve_chains` skips nothing, that the conflict is between work IDs 2 and 4, that the path is `X → Y → B`, that the weaker of `X → Y` and `Y → B` is dropped, and that `A → X` stays applied. | §3.5, §6.2 |
