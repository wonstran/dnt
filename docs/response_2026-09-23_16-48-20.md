# Response: dnt 0.3.3 correctness and packaging implementation plan

Responding to: [review_2026-09-23_16-48-20.md](review_2026-09-23_16-48-20.md)  
Plan (revised): [2026-09-23-dnt-0.3.3-correctness-packaging.md](superpowers/plans/2026-09-23-dnt-0.3.3-correctness-packaging.md)

I accepted all six points and revised the plan. Items 1, 2, 4, 5 and 6 are handled by rewriting Task 20 (golden tooling); item 3 is handled in Task 17 (packaging). Task 21 and Task 24 have follow-on edits. The golden generation logic now lives in testable functions in `tools/golden_cases.py`, so every exemption and fail-closed path is covered by unit tests that need no clip. Findings marked *verified* were checked against the repository.

---

1. **High: a permitted golden exemption could not pass the release gates.** **Accepted.**
   - **The defects-file test now checks validity, not emptiness.** `test_known_defects_file_starts_empty` is replaced by `test_repository_defects_file_is_valid`. It runs the new `load_defects()` validator, which accepts an empty list or reviewed entries alike, so adding a reviewed entry no longer breaks the default suite.
   - **Post-processing runs only where a baseline track file exists.** `make_golden.py` now calls `run_post_cases()`, which post-processes only cases whose status is `ok` and records `skipped: known_defect` for the rest in `manifest["post"]`. The comparison test skips the post-processing case when `manifest["post"][case] != "ok"`.
   - **Both exemption paths are tested.** `test_exempted_case_recorded_with_evidence` covers an exempted tracking case. `test_post_skipped_for_exempted_post_case` covers an exempted ByteTrack post-processing case. The fail-closed paths are also tested: `test_unmatched_error_aborts_and_saves_traceback` and `test_stale_entry_aborts`.

2. **High: the environment check allowed different torch builds.** **Accepted.**
   - **Full version strings are now compared.** `check_env` no longer strips the `+local` suffix, so `torch==2.10.0` does not match an installed `2.10.0+cpu`. `test_check_env_distinguishes_local_builds` covers this.
   - **Runtime details are recorded and enforced.** A new `runtime_info()` returns the Python version, the full torch version, the torch build (CUDA version or `cpu`) and the GPU with its driver. `make_golden.py` writes all of these into the manifest. `test_environment_matches_recorded_environment` then asserts that Python, torch and the torch build equal the recorded values, in addition to the lock-file versions and the clip hash.
   - **Deterministic detection is enforced only on the recorded GPU.** When the manifest claims deterministic detection, `test_detection` first asserts that the current GPU name and driver equal the recorded ones. Tracking runs on the CPU, so it doesn't depend on the GPU.
   - **Both environments use the same interpreter.** Task 21 now builds the comparison venv from the baseline venv's interpreter, so the Python-version check can pass. Task 2 says the same.

3. **High: the wheel rules left out tracked model weights, and the smoke test couldn't notice.** **Accepted.** I resolved it by bundling the weights.

   *Verified:* `Tracker()` defaults to BoT-SORT and resolves `osnet_x1_0_msmt17.pt` under `REID_WEIGHTS_DIR`, inside the installed package (`tracker.py:636`, `:945`). `SignalDetector` looks for `weights/ped_signal.pt` there too, and downloads it from the USF server if it is missing (`signal/detector.py:121–124`). The 0.3.2.4 wheel contained only `.py` files, so both weights have been downloaded on first use until now. `wb_ped_signal.pt` (43 MB) is not referenced anywhere.

   Changes in Task 17:
   - **The wheel includes the two referenced weights.** `package-data` and `MANIFEST.in` now include `track/reid_weights/osnet_x1_0_msmt17.pt` (11 MB) and `detect/signal/weights/ped_signal.pt` (43 MB). The wheel grows to about 54 MB, which is under PyPI's 100 MB per-file limit. `wb_ped_signal.pt` and the `:Zone.Identifier` files stay out.
   - **The wheel contents are asserted.** New `test_wheel_bundles_referenced_weights_only` checks that both weights are present, and that the unreferenced weight and the `Zone.Identifier` files are absent.
   - **The smoke pipeline exercises code paths that use the weights.** After the ByteTrack pipeline, `smoke_pipeline.py` does three things:
     - checks that both installed weights exist and have the repository's SHA-256
     - runs the **default `Tracker()`** (BoT-SORT with ReID) on the synthetic clip, and asserts that the OSNet file was not re-downloaded or overwritten (its mtime is unchanged)
     - constructs a `SignalDetector` with `download_file` replaced by a function that fails, which proves the bundled `ped_signal.pt` is loaded without a download
   - The changelog and Task 24's artifact check (which now also lists the `.pt` files and the approximate wheel size) have been updated to match.
   - **Decision for you:** spec §4.1 listed only the `.names` files as package data. The plan records this as a spec correction. The alternative the review offers is to keep 0.3.2.4's download-on-first-use behaviour, document it, and test it with network access in CI. I chose bundling because the default `Tracker()` then works offline, the test is deterministic, and CI doesn't depend on Google Drive through `gdown`. If you prefer the download approach, tell me and I'll swap Task 17 back.

4. **Medium: the tolerant detection comparison missed schema regressions.** **Accepted.** In the tolerant (non-deterministic) branch of `test_detection`, columns 0, 1 and 7 (frame, `res` and class) must now match exactly, row for row. The ±1 px tolerance still applies to x, y, w and h, and ±0.01 to the confidence.

5. **Medium: reviewed-defect evidence was not carried into the manifest.** **Accepted.**
   - **`load_defects()` validates every entry before any tracker runs:**
     - all required keys are present: `id`, `tracker`, `exception_type`, `message_regex`, `raised_at`, `root_cause`, `reviewed_by`, `reviewed_on` and `evidence`
     - ids are unique, and there is at most one entry per case
     - the case name is known
     - `reviewed_on` is an ISO date
     - the evidence file exists, and its `evidence_sha256` is computed

     `test_invalid_defect_entries_rejected` covers each of these rejections.
   - **The exemption is recorded in the manifest.** For an exempted case, `run_track_cases()` stores the actual traceback as `traceback_<case>.txt` and records `defect_id`, `traceback_sha256` and `evidence_sha256`. The manifest also records `defects_file_sha256`.
   - **The comparison test audits the exemption actually used.** It checks that the entry still exists, that its evidence hash is unchanged, and that the stored traceback matches its recorded hash.
   - **Unexpected errors leave evidence for review.** On an unmatched error the run now writes `unexpected_<case>.txt` before aborting. Task 21 says how the maintainer may turn that file into the evidence for a reviewed entry: in a separate commit, and never done by the implementer.

6. **Low: `bench.py --stages` didn't support its advertised subsets.** **Accepted.** I implemented the subsets rather than narrowing the command line.
   - **New `plan_stages()` validation.** It rejects unknown stages, `track` without `detect` unless `--dets` is given, and `post` without `track` unless `--tracks` is given. Rejections are reported as argparse errors.
   - **Each stage runs only when selected.** Detection runs only if `detect` is selected. Post-processing uses the ByteTrack output from `track`, or else the `--tracks` file.
   - **Tests:** `test_bench_rejects_unsatisfiable_stages` and `test_bench_isolated_stages_with_inputs`.
