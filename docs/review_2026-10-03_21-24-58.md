# Follow-up review of track dedup design, revision 2

Reviewed: 2026-10-03 21:24:58 EDT  
Spec: [2026-10-03-track-dedup-design.md](superpowers/specs/2026-10-03-track-dedup-design.md) (rev. 2)  
Response: [response_2026-10-03_21-45-00.md](response_2026-10-03_21-45-00.md)  
Previous review: [review_2026-10-03_21-13-21.md](review_2026-10-03_21-13-21.md)

The revision substantially addresses the seven original comments. The occupancy formula, fully co-observed negative cases, deterministic edge processing and dropped-row attribution, orphan hand-off, and composed output-ID mapping now have explicit contracts. The response correctly distinguishes proposed behavior from verified implementation. The remaining comments below concern gaps in those contracts; the spec is not yet ready for implementation without resolving them.

1. **[P1] §3.5, cannot-link rule 2: a short dense overlap can still be merged through a bridge.** Component conflict checks inherit the minimum span and observation gates used to generate proposals. At 30 fps, A and C can be observed together on all 20 frames of their overlap, with distinct boxes, yet have neither a MERGE proposal nor a cannot-link constraint because the overlap is shorter than one second. If A/B and B/C separately meet the gates and are accepted, the procedure puts A and C into one component and discards one person's rows on those 20 frames. The occupancy protection for two people observed on most of the same frames therefore has a threshold-dependent exception. Separate proposal eligibility from component safety: specify how dense cross-component overlaps below the proposal thresholds are handled, potentially deferring the join when evidence is insufficient. Add a bridge case with A/C just below the span gate, and another below `min_observed`, rather than testing only a dense A/C that qualifies for evaluation.

2. **[P2] §3.3: canonical lineage order breaks the positional association with `tracks`.** The parent event contract records one lineage entry for each involved track. Existing evidence code interprets `lineage[0]` as track A and `lineage[1]` as track B. Revision 2 instead orders `tracks` by representative selection and `lineage` by raw span, so the two lists can disagree. For example, the earlier-starting representative can have raw ID 125 while the later-starting member has raw ID 122: the track order starts with 125, but the lineage order starts with 122. A MERGE evidence method reusing the existing convention would label the crops with the wrong track IDs, and ledger consumers cannot reconstruct the intended association from those two lists alone. Either canonicalize only the lineage passed into key computation while storing event lineage in track order, or store an explicit association/permutation and require consumers to use it. Extend the reversed-work-ID test to assert correct crop labels, track/lineage correspondence, and `n_a`/`n_b` correspondence, as well as key stability.

3. **[P2] §§3.5 and 5, test 15: accepted-but-skipped cards need a report-selection contract.** The spec promises that a reviewer sees the accepted edge and its conflict evidence, and that a skipped event produces a card. However, §3.4 still describes cards for pending events, and the inherited `write_review` implementation selects only `HUMAN_PENDING` events and removes the report when none exist. Redundant and conflicting events explicitly retain an accepted decision, so simply adding a MERGE card renderer does not make them visible. Specify whether the report also includes accepted-but-skipped MERGEs, or whether a separate diagnostic/audit view shows them; define controls and decision export for those cards. Add a run with only accepted edges, one skipped as conflict, and no pending events, and assert the promised diagnostic view is produced.

4. **[P2] §3.2 and the response's comment-1 resolution: the 125/134 ratio is not established by the measured table.** The formula is `6 / min(30, n_134)`, but §1 marks `n_134` as unmeasured. Thus `6/30 = 0.20` is a lower bound, not a verified exact value, and the one-third penalty is conditional on `n_134 >= 30`. If `n_134 = 15`, for example, occupancy reaches 0.40 and the pair is vetoed. Label both the ratio and penalty as conditional until the overlap counts are measured; do not present the response's paper arithmetic as an established signal. Calibration is already deferred appropriately. Also correct test 1's expectation of “all observed rows”: seven shared frames necessarily discard seven rows under the specified merge rule, so the retained count is 176 rather than 183, with the seven discarded rows accounted for in the ledger.

5. **[P2] §3.5: define whether downstream lineage excludes discarded observations.** Recording `dropped` runs identifies the deletions, but the current `lineage_of_rows` reconstructs only each raw ID's minimum and maximum surviving frame. If raw 122 retains frames before and after a dropped interior row, its downstream lineage still includes that dropped frame. `track_embeddings` requests all clean raw embeddings inside those spans, and `EvidenceBuilder` reads the raw observations in the spans, so the dropped observation can influence later LINK scoring or appear as evidence for the consolidated track despite not being in its work table. Specify whether raw-span evidence intentionally includes discarded observations or must be filtered to retained `(raw_id, frame)` rows. If exclusion is intended, carry a retained-row mask or exact spans through the relevant consumers; merely logging the deletions is insufficient. Add an interior deletion case and verify the downstream appearance/evidence sample set.

This was a static review of the revised spec, response, and current event, evidence, review, lineage, and embedding consumers. No implementation or real-data tests were run; the numeric defaults and real-data success criterion remain unverified as stated in the response.
