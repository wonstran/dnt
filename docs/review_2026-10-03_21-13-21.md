# Review of track dedup design

Reviewed: 2026-10-03 21:13:21 EDT  
Spec: [2026-10-03-track-dedup-design.md](superpowers/specs/2026-10-03-track-dedup-design.md)

Static review against the parent spec and the current `src/dnt/refine` implementation. P1 comments affect identity correctness or the motivating regression; P2 comments need a defined implementation contract.

1. **[P1] §3.2: define the `cooccur` denominator and the zero-shared case.** The table currently reads as `distinct_shared_frames / shared_frames`. With that interpretation, the motivating 122/125 pair has `cooccur = 7/7 = 1` because its shared-frame mean IoU is 0.00, and its score is zero under the proposed defaults. The statement that seven shared frames fall below `cooccur_lo` requires a different denominator. Specify an exact formula (overlap length, union of observed frames, or another explicitly chosen count), define the value when `shared == 0`, and record the numerator and denominator in signals. Test the actual shared-frame IoUs and observation counts, rather than only the number seven.

2. **[P1] §3.2 and success criterion 2: full co-observation can still auto-merge two people.** Two fully observed parallel trajectories with equal-sized boxes offset horizontally by one-third of their width have IoU 0.50 on every frame. With the starting defaults and no appearance provider, `comotion = 0.50`, `cooccur = 0` (none of the boxes fall below `distinct_iou = 0.30`), and `S_dedup = 1`. Both real people are merged and one observation is dropped on every frame. The current side-by-side test only protects pairs whose boxes meet the low-IoU definition of distinct. Add an interleaving/co-observation occupancy condition, or route dense co-observation to review, and cover overlapping parallel boxes as well as disjoint boxes. Specify how genuine simultaneous duplicate detections should be handled if they remain in scope.

3. **[P1] §3.5: pair acceptance is not sufficient for safe union-find groups.** Accepting A/B and B/C merges A/C too, even when A/C has strong distinct co-observation evidence or a recorded rejection. Keeping one row per frame only enforces table uniqueness; it does not check that the component represents one person, and it can silently delete observations of a second person. Define a deterministic component conflict rule before unioning, including how explicit human rejections constrain components. Add a three-track regression with accepted bridge edges and a contradictory A/C pair; preserve the conflict and make any accepted-but-unapplied event explicit in the ledger. The all-positive three-way test does not exercise this failure.

4. **[P2] §§3.4–3.5 and 9: integrate accepted and pending merges with the orphan pass.** `_Stages._orphans` currently receives only linked representatives and pending LINK endpoints. `propose_orphans` measures duration as observed-row count divided by fps, so a sparse track can meet dedup's span-overlap gate yet still be eligible for an orphan drop. Under the proposed table-only handoff, a pending MERGE endpoint can disappear before review, and an accepted merged representative is not protected like a linked track. Define whether accepted merges protect their representatives and pending merges defer orphan decisions. Carry the relevant sets through link's representative mapping and test both paths, including `link.enabled: false`.

5. **[P2] §§3.3, 4 and test 9: canonicalize the unordered pair's lineage independently of work IDs.** `proposal_key` hashes the lineage list in its supplied order; it does not sort it (`events.py`). When two tracks start on the same frame, §3.3 orders them by work ID. Renumbering those IDs can reverse the two lineage entries and change the key, even though the underlying raw spans and overlap are identical. Keep any representative-selection order separate from a canonical key order based on immutable raw lineage. Clarify that test 9 renumbers work-table IDs while retaining raw IDs, and include an equal-start pair whose work-ID ordering reverses.

6. **[P2] §5: define how absorbed IDs resolve to final output IDs.** The current final `renumber` map includes only IDs surviving in the table, and `review._output_ids` looks up `event.tracks` directly in that map. A pending A/C MERGE can coexist with an accepted A/B merge that absorbs A into B; a later LINK can absorb B again. Without composed representative mappings, the pending card and its clip snippet omit A's output trajectory. `signals.merged_into` on accepted events alone does not fix pending events or later absorption. Define and compose dedup/link/final-renumber mappings for review and ledger consumers, and test a pending pair whose endpoint is absorbed by an accepted merge and then a link.

7. **[P2] §3.5 step 3: specify dropped-row attribution for multi-edge components.** With A/B, B/C and A/C accepted and all three having a row on one frame, the component drops two rows, but there is no unique pairwise owner for either deletion. Assigning the component count to every event would report six dropped rows; applying pairs in sequence can instead make attribution depend on enumeration order. Define whether `dropped_rows` is a component total or an event-attributed count, how redundant accepted edges are marked, and how the ledger identifies discarded versus retained raw observations. Add a cyclic three-way case with score ties and shuffled proposal order, checking identical output and unambiguous counts.
