## Comments

1. **[P1] Discard an answer object when `_check` rejects it.** In Task 4, `answer` is assigned before `_check` runs (plan lines 1772–1776). If validation raises `ValueError`, the handler breaks without clearing `answer`, and lines 1788–1789 return that invalid object as a successful answer. The proposed `test_a_backend_returning_a_bad_answer_object_is_treated_as_invalid_output` fails against the revised code. I also reproduced successful verdicts for an out-of-option answer and confidence 1.5, both with zero retries. With three votes, three NaN confidences become a valid-looking majority confidence of 1.0, bypassing the new finite-confidence guard in routing. Clear the rejected object or return success only after validation succeeds; retain the existing regression test and add the multi-vote case.

2. **[P1] Establish ownership before overwriting images or starting a manifest.** Task 8 protects unrelated names during cleanup, but `write_review` still writes `<event id>.jpg` unconditionally and creates a manifest whenever `written` is nonempty (lines 4040–4054). That condition does not establish that the report created the directory, despite the accompanying comment and response. I precreated `o.review/switch-r0-000001.jpg` without a manifest: a pending report overwrote its contents, recorded it as owned, and the next no-pending run deleted it. The input-collision guard does not protect a user's file that is not an input. Choose an unused owned location or reject collisions with unowned files before writing; also preserve an unowned `manifest.json`. Test a foreign directory containing a colliding image name through both the pending write and cleanup.

3. **[P2] Expose retry invocations in the persisted summary.** Task 4 adds `runner.retries`, and Task 9 says retries are reported, but Task 7's `_vlm_counts` omits that counter (lines 3235–3244). It is consequently absent from the result, ledger summary, and CLI output. In the reproduced six-invocation case below, the persisted summary would report only `calls=1` with no retry count. Add `retries` to both branches of `_vlm_counts`, the summary contract/spec follow-up, and the tests that pin its keys. Verify a run with a retry, not just a zero-retry run.

4. **[P2] Validate the manifest's `images` collection before iterating it.** `_listed_images` catches errors while loading and indexing JSON, but iterates `names` outside that guard (lines 3978–3984). A readable manifest containing `{"images": null}` raises `TypeError`; `{"images": 1}` does likewise. I reproduced the null case through `_remove_own_files`. Since the review writer is called before output/ledger completion, a damaged report manifest can prevent a successful refinement from being written. Require a list of names and treat malformed collections as having no proven ownership. Add pending and no-pending rerun tests for readable but invalid manifests.

5. **[P2] Update the old empty-evidence test to match observed screen crops.** Task 5's `test_an_event_with_nothing_to_draw_gives_none` (lines 2074–2080) still creates an all-occluded DROP with valid observed rows and no context, then expects an empty plan. The new screen rule intentionally retains those rows. The extracted planner returned six row-A crops and `is_empty=False` for that test's scenario, so the prescribed Task 5 gate cannot pass. Use an identity event with no clean rows, or a screen event with no valid observed rows, to test genuinely empty evidence. Keep the new overlapping-screen test as the positive case.

## Retry-budget decision

I recommend keeping `max_calls` as a hard limit on actual backend invocations, including retries. The new policy is explicit in the response, but weakens the cost-control requirement in Review Focus item 2. The extracted runner made **six backend invocations with `max_calls=1`**: two transient failures, an invalid reply, two more transient failures, then a valid reply. Thus a budget of 500 can permit 3,000 invocations. Priority admission should reserve capacity for complete questions while retries draw from a bounded allowance; when an allowance is exhausted, leave the affected question pending. If the intended product decision is instead to budget votes, name that limit accordingly and provide a separate invocation limit. The missing summary counter in comment 3 applies under either policy.
